2MQ6 — Why does Java not support multiple inheritance through classes? How is this limitation addressed?

The Diamond Problem

If class C extends both A and B, and both override the same method, the compiler cannot determine which version to inherit — causing ambiguity.

A / \ B C ← B and C both override method() \ / D ← Which method() does D inherit? AMBIGUOUS!

Java's Solution: Interfaces

A class can implement multiple interfaces. If a conflict arises with default methods (Java 8+), the implementing class must explicitly override the ambiguous method.

interface A { default void show() { System.out.println("A"); } }
interface B { default void show() { System.out.println("B"); } }
class C implements A, B {
    public void show() { A.super.show(); }  // explicit resolution
}
💡 Concept Booster
The Diamond Problem is like asking "whose surname do I inherit if both grandparents have conflicting traditions?" Java avoids this for classes. With interfaces, the child must explicitly choose — resolving ambiguity without the confusion.

7MQ1 — Define Abstraction and Encapsulation. Explain how these concepts are implemented in Java using access modifiers and abstract classes/interfaces. Include a code example.

1. Abstraction

Abstraction is the OOP principle of hiding implementation details and exposing only the essential features to the user. It reduces complexity and increases code modularity. In Java, abstraction is achieved via abstract classes (partial abstraction) and interfaces (full abstraction).

2. Encapsulation

Encapsulation is the principle of binding data (fields) and methods together in a single unit (class) and restricting direct access to internal state. Achieved via access modifiers (private, protected, public) combined with getter/setter methods.

3. Access Modifiers (Encapsulation Backbone)

ModifierSame ClassSame PackageSubclassOther Classes
private✓✗✗✗
default✓✓✗✗
protected✓✓✓✗
public✓✓✓✓

4. Code Example

// ── Abstraction via Abstract Class ──
abstract class Shape {
    abstract double area();             // abstract — no body
    void display() {                    // concrete method
        System.out.println("Area: " + area());
    }
}

// ── Encapsulation via private fields + getters/setters ──
class Circle extends Shape {
    private double radius;              // private — encapsulated

    public void setRadius(double r) {
        if (r > 0) radius = r;          // validation in setter
    }
    public double getRadius() { return radius; }

    @Override
    double area() { return Math.PI * radius * radius; }
}

// ── Interface for Pure Abstraction ──
interface Drawable {
    void draw();                        // contract — no implementation
}

class Square extends Shape implements Drawable {
    private double side;
    Square(double s) { this.side = s; }

    @Override double area() { return side * side; }
    @Override public void draw() { System.out.println("Drawing Square"); }
}

public class Main {
    public static void main(String[] args) {
        Circle c = new Circle();
        c.setRadius(5);
        c.display();       // Area: 78.53...

        Square sq = new Square(4);
        sq.display();      // Area: 16.0
        sq.draw();         // Drawing Square
    }
}

5. Key Rules

  • Abstract class cannot be instantiated directly.
  • A class with even one abstract method must be declared abstract.
  • Use private for all fields; provide controlled access via public getters/setters.
💡 Concept Booster
Abstraction = TV remote — you press buttons without knowing the circuit. Encapsulation = medicine capsule — the drug (data) is inside, protected. Together: abstraction hides complexity; encapsulation protects data. Both are cornerstones of maintainable, scalable Java design.
7MQ2 — Explain the concept of Constructors. Discuss Default, Parameterized, and Copy constructors in Java, providing code snippets for each.

1. What is a Constructor?

A constructor is a special method that is automatically invoked when an object is created using new. It has the same name as the class, no return type, and is used to initialise object state. Constructors can be overloaded.

2. Default Constructor

No parameters. Provides default values. If not explicitly defined, the compiler auto-generates one (all fields set to their default: 0, null, false).

class Student {
    String name;
    int age;

    Student() {                         // default constructor
        name = "Unknown";
        age  = 0;
    }
}
Student s = new Student();              // name="Unknown", age=0

3. Parameterized Constructor

Accepts arguments to initialise fields with user-provided values. Enables creating objects with specific state at creation time.

class Student {
    String name;
    int age;

    Student(String n, int a) {          // parameterized constructor
        this.name = n;
        this.age  = a;
    }
}
Student s = new Student("Alice", 20);   // name="Alice", age=20

4. Copy Constructor

Takes an object of the same class as parameter and copies its field values. Java does not provide a built-in copy constructor (unlike C++); it must be written manually.

class Student {
    String name;
    int age;

    Student(Student other) {            // copy constructor
        this.name = other.name;
        this.age  = other.age;
    }
}
Student s1 = new Student("Bob", 21);
Student s2 = new Student(s1);           // s2 is an independent copy of s1

5. Constructor Chaining with this()

class Student {
    String name; int age;
    Student() { this("Default", 18); }          // calls parameterized
    Student(String n, int a) { name = n; age = a; }
}

6. Comparison

TypeParametersPurpose
DefaultNoneInitialises with default values
ParameterizedUser-definedCustom initialisation at creation
CopySame-class objectCreates an independent duplicate
💡 Concept Booster
A constructor is like a college registration form. Default = blank form with pre-filled defaults. Parameterized = form with your own details. Copy = photocopying someone else's filled form. Each serves a distinct initialisation purpose.
7MQ3 — "Java is strictly call-by-value." Explain this statement in detail, specifically focusing on how object references are handled during function calls.

1. Call-by-Value — The Rule

Java always passes arguments by value. This means a copy of the variable is passed to the method. For primitives, the actual value is copied. For objects, the reference (memory address) is copied — but it is still a copy of the reference, not the object itself.

2. Case 1 — Primitives

class Test {
    static void change(int x) {
        x = 100;                        // modifies only the local copy
    }
    public static void main(String[] args) {
        int a = 5;
        change(a);
        System.out.println(a);          // still 5 — original unchanged
    }
}

3. Case 2 — Objects (Reference Copied)

class Dog {
    String name;
    Dog(String n) { this.name = n; }
}
class Test {
    static void modify(Dog d) {
        d.name = "Max";                 // affects the SAME object in heap
    }
    static void reassign(Dog d) {
        d = new Dog("Rocky");           // only local copy changes; caller unaffected
    }
    public static void main(String[] args) {
        Dog myDog = new Dog("Rex");
        modify(myDog);
        System.out.println(myDog.name); // "Max" — field change persists

        reassign(myDog);
        System.out.println(myDog.name); // still "Max" — reassign had no effect
    }
}

4. Memory Diagram

Caller stack Heap ┌──────────┐ ┌──────────────┐ │ myDog ───┼────────►│ Dog{name=Rex}│ └──────────┘ └──────────────┘ │ Method stack (copy) ┌──────────┐ │ d ────┼────────► same heap object └──────────┘ d.name = "Max" → changes heap object → caller sees "Max" d = new Dog() → d points to a new heap object → caller's myDog UNCHANGED

5. Key Takeaway

  • Java passes the value of the reference, not the reference itself.
  • Field modifications through the copied reference do affect the original object.
  • Reassigning the reference inside the method does not affect the caller's variable.
💡 Concept Booster
Imagine giving someone a photocopy of your house key. They can enter and rearrange furniture (modify object fields — caller sees changes). But if they throw the copy away and cut a new key (reassign reference), your original key is completely unaffected. Java always hands over the copy — never the original key.
7MQ4 — Define Polymorphism. Provide a detailed comparison between Method Overloading (Compile-time) and Method Overriding (Run-time) with implementation examples.

1. Polymorphism

Polymorphism means "many forms." It allows one interface to be used for different underlying data types or behaviours. Java supports two types: Compile-time (Method Overloading) and Run-time (Method Overriding).

2. Method Overloading — Compile-Time Polymorphism

Multiple methods in the same class with the same name but different parameter lists. Resolved by the compiler at compile time (static binding).

class Calculator {
    int add(int a, int b)             { return a + b; }
    double add(double a, double b)    { return a + b; }   // different types
    int add(int a, int b, int c)      { return a + b + c; } // different count

    public static void main(String[] args) {
        Calculator c = new Calculator();
        System.out.println(c.add(2, 3));       // 5   (int version)
        System.out.println(c.add(2.5, 3.5));   // 6.0 (double version)
        System.out.println(c.add(1, 2, 3));    // 6   (3-arg version)
    }
}

3. Method Overriding — Run-Time Polymorphism

A subclass provides its own implementation of a method already defined in the parent class with the same signature. Resolved at runtime via dynamic dispatch (late binding).

class Animal {
    void speak() { System.out.println("Animal makes a sound"); }
}
class Dog extends Animal {
    @Override
    void speak() { System.out.println("Dog says: Woof!"); }
}
class Cat extends Animal {
    @Override
    void speak() { System.out.println("Cat says: Meow!"); }
}
public class Main {
    public static void main(String[] args) {
        Animal a1 = new Dog();  // runtime type = Dog
        Animal a2 = new Cat();  // runtime type = Cat
        a1.speak();             // Woof! (dynamic dispatch)
        a2.speak();             // Meow!
    }
}

4. Comparison

FeatureOverloadingOverriding
TypeCompile-time (static binding)Run-time (dynamic binding)
LocationSame classParent class → Child class
SignatureMust differ (params)Must be identical
Return TypeCan be differentMust be same (or covariant)
Access ModifierCan be anythingCannot be more restrictive
@OverrideNot usedRecommended
💡 Concept Booster
Overloading is a chef cooking differently based on ingredients given (decided at order time — compile). Overriding is a child using their own accent instead of their parent's (decided at runtime based on the actual object). The JVM uses a virtual method table (vtable) to dispatch overridden calls dynamically.
7MQ5 — Illustrate the various types of Inheritance supported in Java. Explain the "Diamond Problem" and how Java uses Interfaces to achieve multiple inheritance.

1. Inheritance

Inheritance is an OOP mechanism where a child class acquires the properties and behaviours of a parent class. It promotes code reusability and establishes an IS-A relationship.

2. Types of Inheritance in Java

TypeStructureSupport
SingleA → B (one parent, one child)Classes ✓
MultilevelA → B → C (chain)Classes ✓
HierarchicalA → B and A → C (one parent, many children)Classes ✓
MultipleA + B → C (multiple parents)Interfaces only ✓
HybridCombination of aboveInterfaces only ✓

3. Code — Multilevel Inheritance

class Animal { void eat()  { System.out.println("Eating"); } }
class Dog    extends Animal { void bark() { System.out.println("Barking"); } }
class Puppy  extends Dog    { void play() { System.out.println("Playing"); } }

Puppy p = new Puppy();
p.eat(); p.bark(); p.play();  // all methods accessible

4. The Diamond Problem

When class D extends both B and C (both of which extend A and override its method), the compiler cannot resolve which version D should inherit — causing ambiguity.

A (has method display()) / \ B C (both override display()) \ / D ← Inherits from both — AMBIGUOUS! Not allowed in Java for classes.

5. Solution via Interfaces (Java 8+ Default Methods)

interface B { default void show() { System.out.println("B"); } }
interface C { default void show() { System.out.println("C"); } }

class D implements B, C {
    @Override
    public void show() {
        B.super.show();   // explicitly resolve conflict
        C.super.show();
    }
}
new D().show(); // B   C

6. Key Points

  • Java supports single inheritance for classes to avoid the Diamond Problem.
  • Multiple inheritance is supported through interfaces.
  • With conflicting default methods, the implementing class must override.
💡 Concept Booster
The Diamond Problem is like two parents giving conflicting instructions — the child is confused. Java avoids this for classes by restricting to single inheritance. For interfaces, the child must explicitly resolve the conflict, making intent clear and unambiguous. Interfaces with default methods (Java 8) are the key enabler.

2. Creating Threads

// Method 1: Extend Thread
class MyThread extends Thread {
    public void run() { System.out.println("Thread: " + getName()); }

3. Thread Synchronization

Problem: When multiple threads access a shared resource concurrently, they may interleave in unpredictable ways causing Race Conditions and data inconsistency.

Solution: The synchronized keyword ensures only one thread at a time can execute a block or method by acquiring the object's monitor lock.

class Counter {
    private int count = 0;

    // synchronized method — only one thread can execute at a time
    synchronized void increment() { count++; }
    synchronized int getCount()   { return count; }
}

class Main {
    public static void main(String[] args) throws InterruptedException {
        Counter c = new Counter();

        Thread t1 = new Thread(() -> { for(int i=0; i<1000; i++) c.increment(); });
        Thread t2 = new Thread(() -> { for(int i=0; i<1000; i++) c.increment(); });

        t1.start(); t2.start();
        t1.join();  t2.join();

        System.out.println("Final count: " + c.getCount()); // always 2000
    }
}

4. Synchronized Block (finer control)

synchronized(this) {
    // only the critical section is locked, not the whole method
    count++;
}
💡 Concept Booster
Threads are multiple workers sharing one printer. Without sync, two workers print simultaneously — garbled output (race condition). synchronized puts a lock on the printer — only one worker at a time. The monitor lock is automatically released when the block exits, ensuring safe concurrent access without deadlock (as long as locks are acquired in consistent order).

7MQ8 — What is Exception Handling? Explain the robust error-handling mechanism in Java using try, catch, finally, throw, and throws.

1. Exception Handling

Exception handling is a mechanism to handle runtime errors gracefully, preventing abnormal program termination and enabling recovery. Java uses a structured try-catch-finally model built on the Throwable hierarchy.

2. Exception Hierarchy

java.lang.Throwable ├── Error (JVM errors — don't catch these) │ ├── StackOverflowError │ └── OutOfMemoryError └── Exception ├── Checked Exceptions (must handle — IOException, SQLException) └── RuntimeException (unchecked — NullPointerException, etc.)

3. Keywords Explained

KeywordRole
tryWraps code that may throw an exception. Must be followed by catch or finally.
catchCatches and handles a specific exception type. Multiple catch blocks are allowed.
finallyAlways executes — even if exception is thrown or caught. Used for cleanup (close files, DB connections).
throwManually throws an exception object inside a method: throw new IOException("msg");
throwsDeclares in method signature that it may throw checked exceptions. Responsibility passed to caller.

4. Complete Example

class InsufficientFundsException extends Exception {   // custom exception
    InsufficientFundsException(String msg) { super(msg); }
}

class BankAccount {
    double balance = 1000;

    void withdraw(double amt) throws InsufficientFundsException {  // throws
        if (amt > balance)
            throw new InsufficientFundsException("Need: " + amt + ", Have: " + balance); // throw
        balance -= amt;
        System.out.println("Withdrawn: " + amt);
    }
}

public class Main {
    public static void main(String[] args) {
        BankAccount acc = new BankAccount();
        try {                                        // try
            acc.withdraw(500);                       // success
            acc.withdraw(800);                       // throws exception
        } catch (InsufficientFundsException e) {     // catch
            System.out.println("Error: " + e.getMessage());
        } catch (Exception e) {                      // catch-all
            System.out.println("Unexpected: " + e);
        } finally {                                  // finally
            System.out.println("Transaction session ended.");  // always runs
        }
    }
}
/* Output:
   Withdrawn: 500.0
   Error: Need: 800.0, Have: 500.0
   Transaction session ended.  ← finally always runs */

5. Multi-catch (Java 7+)

catch (IOException | SQLException e) { e.printStackTrace(); }  // cleaner
💡 Concept Booster
try = the risky zone. catch = the safety net. finally = the cleanup crew (always shows up, even after a crash). throw = manually triggering an alarm. throws = a warning sign on the method door saying "this may explode — caller must handle it." Together they form Java's complete, layered error-handling mechanism.
7MQ9 — Discuss String handling in Java. Explain why the String class is immutable and compare it with StringBuilder and StringBuffer.

1. String in Java

Strings in Java are objects of the java.lang.String class. Java provides a String Constant Pool (SCP) in the heap — when a string literal is created, the JVM checks the pool first. If it exists, it returns the same reference (interning).

String s1 = "Hello";             // stored in String Pool
String s2 = "Hello";             // s2 points to same pool object as s1
String s3 = new String("Hello"); // forces new heap object (outside pool)

2. Why String is Immutable

Once a String object is created, its value cannot be changed. Any modification creates a new String object.

  • Security: Strings are used in class loading, network connections, DB URLs — immutability prevents tampering.
  • Thread Safety: Multiple threads can share the same String without synchronisation.
  • Hashcode Caching: Immutable strings cache their hashcode — important for use as HashMap keys.
  • String Pool: Possible only because the value never changes after creation.
String s = "Hello";
s = s + " World";   // does NOT modify "Hello" — creates NEW object "Hello World"
// "Hello" still exists in pool until GC collects it

3. StringBuilder and StringBuffer

For heavy string manipulation, use mutable alternatives to avoid creating thousands of intermediate String objects.

StringBuilder sb = new StringBuilder("Hello");
sb.append(" World");           // "Hello World" — modifies same object
sb.insert(5, ",");             // "Hello, World"
sb.reverse();                  // "dlroW ,olleH"
sb.delete(0, 3);               // removes chars from index 0 to 2
System.out.println(sb.length()); // useful methods available

s.replace("World","Java") // "  Hello Java  "
s.split(" ")            // ["", "", "Hello", "World", "", ""]
String.valueOf(42)       // "42"  — primitive to String
💡 Concept Booster
String = a printed book (can't edit, need a new one for every change). StringBuilder = a personal notebook (edit freely, fast, single-user). StringBuffer = a shared whiteboard (multiple users can edit but one at a time — synchronized). For loops with string concatenation, always prefer StringBuilder — it can be 10×+ faster than repeated + on String.
7MQ10 — Explain the core architecture of Spring Boot. Discuss the concepts of Dependency Injection (DI) and Inversion of Control (IoC).

1. What is Spring Boot?

Spring Boot is an opinionated extension of the Spring Framework that enables building production-ready Java applications with minimal configuration. Key features: auto-configuration, embedded server (Tomcat), starter dependencies, and actuator for monitoring.

2. Core Layered Architecture

LayerAnnotationResponsibility
Presentation@RestControllerHandles HTTP requests/responses. Maps URLs to methods. Returns JSON/data.
Service@ServiceContains business logic. Calls Repository for data. Keeps Controllers thin.
Repository / DAO@RepositoryInterfaces with the database using JPA/Hibernate. Abstracts SQL queries.
Model / Entity@EntityRepresents database tables. Plain Java objects (POJOs) with JPA mapping.
Client (Browser/App) │ HTTP Request ▼ @RestController (Presentation Layer) │ calls ▼ @Service (Business Logic Layer) │ calls ▼ @Repository (Data Access Layer) │ queries ▼ Database (MySQL / PostgreSQL / H2 etc.)

3. Inversion of Control (IoC)

IoC is a design principle where the control of object creation and dependency management is transferred from the application code to a framework (the IoC Container). Instead of classes creating their dependencies, the container creates and injects them.

// Without IoC — tight coupling, hard to test
class Car {
    Engine engine = new Engine();   // Car creates its own Engine
}

// With IoC — Spring creates and manages objects (beans)
@Component
class Engine { }

@Component
class Car {
    @Autowired Engine engine;       // Spring injects the Engine bean
}

4. Dependency Injection (DI)

DI is the mechanism by which IoC is implemented — dependencies are "injected" into a class rather than the class creating them itself. Spring supports three types:

DI TypeHowRecommended?
Constructor InjectionDependencies passed via constructor parameter✅ Yes (immutable, testable)
Setter InjectionDependencies set via setter methodOptional dependencies
Field Injection@Autowired directly on field⚠ Avoid (hard to test)

5. Complete Minimal Spring Boot App

@SpringBootApplication          // enables auto-config + component scan
public class App {
    public static void main(String[] args) { SpringApplication.run(App.class, args); }
}

@RestController
class HelloController {
    private final GreetService service;

    HelloController(GreetService service) { // Constructor Injection (recommended)
        this.service = service;
    }

    @GetMapping("/hello")
    String hello() { return service.greet(); }
}

@Service
class GreetService {
    String greet() { return "Hello from Spring Boot!"; }
}

💡 Concept Booster
IoC = Hollywood Principle: "Don't call us, we'll call you." Your class doesn't create its dependencies — Spring's IoC container does. DI is the mechanism: Spring delivers the dependencies to your class's doorstep. Spring Boot makes this effortless with auto-configuration and embedded servers — think of it as a smart factory manager who knows which worker (bean) to assign to each job, wires them up, and starts the factory automatically.
