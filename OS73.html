Process, PCB & State Transitions

7 Marks Define Process. Explain various steps involved in change of a process state with neat transition diagram.
Definition — Process

A process is a program that is currently running. A program sitting on disk is passive (just a file); once loaded into memory and given CPU time, it becomes an active process. It includes: the code being executed, the current instruction (program counter), registers, stack (function calls), heap (dynamic memory), and data section (global variables).

Process States

An OS defines the following states for a process during its lifetime:

  • New — Process is just being created (memory being set up).
  • Ready — Process is in memory, has everything it needs, and is waiting for the CPU to pick it up.
  • Running — Process has the CPU and its instructions are actively executing right now.
  • Waiting (Blocked) — Process is waiting for something outside the CPU (e.g., a file to load, user input, I/O). CPU is free to run someone else.
  • Terminated — Process has finished. OS cleans up its resources.

7 Marks Explain in detail about the Process Control Block (PCB) in CPU Scheduling.
Definition — PCB

A Process Control Block (PCB), also called a Task Control Block, is a data structure the OS keeps for every process — like an ID card for each process. It stores everything the OS needs to manage, pause, and resume a process. It lives in a protected area of OS memory so processes can't tamper with it.

PCB Structure Diagram

Role of PCB in CPU Scheduling

  • When the CPU switches from one process to another (context switch), the OS saves the current process's state (PC, registers, etc.) into its PCB — like saving a game.
  • It then loads the new process's PCB to resume from exactly where it left off — like loading a save file.
  • PCBs are what make multiprogramming possible — multiple processes can share one CPU by taking turns, each remembering its state.
  • The short-term scheduler (dispatcher) reads PCB fields like priority and burst time to decide who gets the CPU next.

Context Switch

Process P0 running ↓ interrupt / system call Save PCB(P0): PC, registers, state → "Ready" Load PCB(P1): PC, registers, state → "Running" ↓ P1 executes Save PCB(P1) → Load PCB(P0) → P0 resumes
Important: Context switch is pure overhead — no useful work happens during it; the CPU is just saving and loading state. Faster CPUs reduce this overhead, but it's still a cost to be aware of.

Definition — Process

A process is a program under execution. When a program is loaded into memory and starts executing, it becomes a process. A process consists of: Text Section (code), Data Section (global variables), Heap (dynamic memory), Stack (function calls & local variables), and Program Counter.

A Process Control Block (PCB) is a kernel data structure that stores all information about a process. It acts as the identity card of a process in the operating system.

Threads & Thread Management

7 Marks Explain in detail about the Threads and their management.
Definition — Thread

A thread is the smallest unit of work the CPU can execute — it's a "mini-process" within a process. Also called a lightweight process (LWP). Multiple threads in the same process share the process's code, data, and open files, but each has its own PC, registers, and stack. Think of a process as a factory and threads as the workers inside it.

Single-Threaded vs Multi-Threaded Process

Benefits of Threads

  • Responsiveness: One thread can handle user input while another downloads data — the app never freezes.
  • Resource Sharing: Threads share code and data automatically — no need for complex IPC mechanisms between them.
  • Economy: Creating a thread is ~30× cheaper (time + memory) than creating a new process.
  • Scalability: On multi-core CPUs, different threads can run on different cores simultaneously — true parallelism.

Types of Threads

TypeUser-Level Threads (ULT)Kernel-Level Threads (KLT)
ManagementManaged by user-space libraryManaged directly by OS kernel
SpeedFaster to create/manageSlower (needs system call)
BlockingOne blocks → all blockOne blocks → others continue
MultiprocessorCannot use multiple CPUsCan run on multiple CPUs
ExamplePOSIX Pthreads (library)Windows threads, Linux NPTL

Thread Models

  • Many-to-One: Many user threads map to 1 kernel thread. Simple but no true parallelism — if one blocks, all block.
  • One-to-One: Each user thread gets its own kernel thread. True parallelism on multi-core. Used by Linux and Windows.
  • Many-to-Many: Many user threads are multiplexed onto a smaller pool of kernel threads. Best balance of flexibility and performance.

Thread Management Operations

  1. Thread Creation: pthread_create() — creates a new thread with a function to execute.
  2. Thread Termination: pthread_exit() — terminates the calling thread voluntarily.
  3. Thread Join: pthread_join() — waits for another thread to finish (synchronization).
  4. Thread Synchronization: Mutexes and semaphores prevent race conditions in shared data.
  5. Thread Scheduling: OS or library schedules threads on available CPU cores.

Scheduling Theory — MLFQ & Partitioning

7 Marks Explain Multilevel Feedback Queue Scheduling and Fixed vs Variable Partitioning.

Multilevel Feedback Queue (MLFQ) Scheduling

Definition

MLFQ uses multiple queues, each with different priority levels and time quantums. Processes start in the highest-priority queue and move down if they use too much CPU time. Short, interactive tasks stay high; long CPU-heavy tasks sink lower. It automatically learns what kind of process each one is.

Structure of MLFQ

  • All new processes enter the highest-priority queue (Q0) — given a short time quantum to see if they finish quickly.
  • If a process uses its full time quantum without finishing → it gets demoted to a lower-priority queue (assumes it's a long CPU job).
  • If a process voluntarily gives up CPU (waits for I/O before time is up) → it stays in its queue or may even be promoted (it's behaving interactively).
  • Lower queues have longer time quantums or FCFS — long jobs are allowed to run for longer stretches, preventing starvation.
  • A process in a higher queue can always preempt one running in a lower queue.
Key advantage: MLFQ favors short interactive processes (like keystrokes) while still allowing long CPU-bound processes to complete eventually.

Fixed Partitioning vs Variable Partitioning

FeatureFixed PartitioningVariable Partitioning
Partition SizeFixed at boot time, cannot changeAllocated dynamically at runtime
Number of PartitionsFixed; limits degree of multiprogrammingVaries; limited only by memory size
FragmentationInternal fragmentation (wasted space inside partition)External fragmentation (holes between allocations)
FlexibilityLess flexible; large processes may not fitMore flexible; partition fits exact process size
Memory UtilizationPoor — wasted space inside each partitionBetter — exact fit reduces waste
OS ComplexitySimple to implementComplex (needs compaction, coalescing)
ExampleIBM OS/360 (early systems)Modern OS like Linux, Windows
Internal Fragmentation

Wasted space inside an allocated partition — the process is smaller than the slot it was given. Example: 40KB process in a 50KB partition → 10KB wasted. Only happens in Fixed Partitioning.

External Fragmentation

Total free memory is enough, but it's scattered in small pieces — no single contiguous block is large enough. Fix: compaction (shuffle memory to merge free holes into one). Happens in Variable Partitioning.

Deadlock — Concepts & Characterization

7 Marks Explain Deadlock and necessary conditions for deadlock. Also explain Resource Allocation Graph (RAG) with suitable diagram.
Definition — Deadlock

A deadlock is when a group of processes are all stuck waiting for resources that are held by each other — and none of them can ever proceed. Like a 4-way traffic gridlock where every car is waiting for the car ahead to move. No one moves. Ever.

Coffman's Four Necessary Conditions for Deadlock

ALL four conditions must hold simultaneously for a deadlock to occur:

1. Mutual Exclusion

At least one resource can only be used by one process at a time — it can't be shared. E.g., a printer printing one job at a time.

2. Hold and Wait

A process is already holding at least one resource, but is also waiting to grab more resources that are currently held by someone else.

3. No Preemption

Resources cannot be forcibly taken away. A process must voluntarily release them when it's done — you can't grab a resource from a process mid-work.

4. Circular Wait

There is a circle of processes, each waiting for a resource held by the next: P0 waits for P1, P1 waits for P2, ..., Pn waits for P0. A closed loop of waiting.

🧠 Memory Trick — 4 Coffman Conditions: "MH-NC" → Mutual exclusion, Hold and wait, No preemption, Circular wait. All 4 must be true simultaneously for deadlock. Break ANY ONE → no deadlock possible.

Resource Allocation Graph (RAG)

RAG is a directed graph used to describe the state of resources and processes in the system.

  • Circles (P) = Processes
  • Rectangles (R) = Resources; dots inside = instances
  • Request Edge (P→R) = Process P requests resource R
  • Assignment Edge (R→P) = Resource R is assigned to process P

RAG with Deadlock

Key Rule: If RAG has NO cycle → NO deadlock. If RAG has a cycle → possibly deadlock. If each resource has only ONE instance → cycle = guaranteed deadlock.

System Model for Deadlock

  • Resources are of types R1, R2, ..., Rm (CPU cycles, memory space, I/O devices, files)
  • Each resource type Ri has Wi instances
  • A process must request → use → release a resource
  • OS uses a wait-for-graph or banker's algorithm to detect/avoid deadlocks
7 Marks Is it possible to have a deadlock involving only a single process? Explain. Also discuss Wait-For Graph method.

Single Process Deadlock — Is It Possible?

Answer

No — classical deadlock cannot occur with a single process. Deadlock requires a circular wait between multiple processes. One process cannot form a circle by itself. However, a single process can block itself in a programming error (self-deadlock), but this is different from OS-level deadlock.

Explanation

  • Classical deadlock needs a circular chain of waiting: P1 waits for P2, P2 waits for P1. One process alone can't form a circle.
  • A process can block itself — e.g., if it tries to acquire a mutex it already holds (non-reentrant lock). This is called a self-deadlock or programming-level deadlock, but the OS won't classify it as a classical deadlock.
  • In some informal contexts, a process requesting a resource it already holds might be said to be in a "degenerate deadlock," but standard OS theory requires ≥ 2 processes.
Exam Answer: "No, classical deadlock requires circular wait among ≥2 processes. A single process may suffer a self-deadlock (programming error), but the OS deadlock model defines it for a SET of processes."

Wait-For Graph (WFG)

Definition

A Wait-For Graph (WFG) is a simplified version of the RAG used for deadlock detection when each resource has only ONE instance. It keeps only processes as nodes and draws a direct edge from Pi to Pk if Pi is waiting for a resource currently held by Pk. If the WFG has a cycle → deadlock.

Construction of Wait-For Graph

  1. Start with the Resource Allocation Graph (RAG).
  2. Remove all resource nodes (rectangles) from the RAG.
  3. If Pi was waiting for resource Rj, and Rj was held by Pk, add an edge Pi → Pk (Pi waits for Pk).
  4. The resulting graph contains only process nodes with directed edges.

Wait-For Graph Diagram

Deadlock Detection using WFG

  • If WFG has a cycle → deadlock exists
  • If no cycle → no deadlock
  • OS periodically runs a cycle-detection algorithm on the WFG
  • Time complexity: O(n²) where n = number of processes

Banker's Algorithm

Banker's Algorithm — Concept

Banker's Algorithm (Dijkstra) is a deadlock avoidance algorithm. Before granting any resource request, it simulates the allocation and checks if the system would still be in a safe state (i.e., all processes can still complete in some order). If yes → grant the request; if no → make the process wait. Like a bank that never lends more than it can recover.

Safe State: A state is safe if there exists a safe sequence — an ordering of all processes such that each process's remaining resource needs can be met using currently available resources + resources freed by earlier processes in the sequence. Safe state = deadlock-free guaranteed.
🧠 Memory Trick — Banker's Safety Check: Think of Work as available cash, Finish[] as "has this customer repaid?" Each round: find a process whose Need ≤ Work, let it finish, add back its Allocation to Work. If everyone reaches Finish=True → SAFE. Key formula: Need = Max − Allocation.

Deadlock Prevention, Avoidance, Detection & Recovery

7 Marks Explain the concept of deadlock and discuss deadlock prevention and avoidance techniques.

Deadlock Handling Strategies Overview

1. Deadlock Prevention

If even one of the four Coffman conditions is broken, deadlock becomes impossible. Here's how to break each one:

Condition to BreakMethodDrawback
Mutual ExclusionMake resources sharable (e.g., read-only files)Not always possible (printer must be exclusive)
Hold and WaitRequest ALL resources at start OR release all before new requestLow resource utilization, starvation possible
No PreemptionIf process can't get resource, release all its current resourcesWorks only for resources with save/restore state
Circular WaitImpose total ordering on resources; request only in increasing orderInconvenient programming; may not reflect true need

2. Deadlock Avoidance

Don't prevent deadlock conditions — instead, be smart about granting requests. Only give resources if the system remains in a safe state afterward. Needs each process to declare its maximum resource needs upfront.

  • Banker's Algorithm (Dijkstra): Simulates allocation for multiple instances. Grants request only if resulting state is safe.
  • Resource Allocation Graph Algorithm: Uses a "claim edge" (dashed) for single-instance resources. Request is granted only if no cycle forms when claim edge becomes assignment edge.
Safe State: ∃ safe sequence ⟨P1, P2, ..., Pn⟩ such that each Pi's remaining needs can be satisfied by currently available + resources held by Pj (j < i)
7 Marks Explain strategies for deadlock prevention, avoidance, detection, and recovery with advantages and disadvantages.

Complete Deadlock Handling Framework

1. Deadlock Prevention

Advantages

Simple logic; deadlock never occurs; no overhead at runtime

Disadvantages

Low device utilization; reduced concurrency; starvation possible

2. Deadlock Avoidance

  • Requires prior knowledge of max resources each process will ever use.
  • Banker's Algorithm: O(n²·m) per request — works for multiple resource instances.
  • RAG with Claim Edges: Simpler, works for single instance only.
Advantages

Deadlock never occurs; more flexible than prevention; allows concurrent access

Disadvantages

Requires advance declaration of max needs; overhead per request; may deny safe requests

3. Deadlock Detection

Let deadlocks happen, but run periodic checks to find them. Once found, take action to break them.

  • Single instance resources: Use a Wait-For Graph; detect cycles. A cycle = deadlock.
  • Multiple instance resources: Use the detection algorithm (like Banker's but using current allocations, not maximums).
  • How often to detect: More frequent = faster recovery but more CPU overhead. Less frequent = cheaper but deadlocks linger longer.
Detection Algorithm (Multiple Instances): 1. Work = Available 2. Initialize Finish[]: - If Allocation[i] == 0 (process holds nothing) → Finish[i] = True - Else → Finish[i] = False 3. Find process Pi where: Finish[i] = False AND Request[i] ≤ Work → Work = Work + Allocation[i]; Finish[i] = True; Goto step 3 4. If any Finish[i] = False → DEADLOCK involving those processes
Advantages

No restrictions on resource allocation; maximum concurrency; simple implementation

Disadvantages

Deadlocks DO occur; recovery is expensive; detection overhead; starvation during recovery

4. Deadlock Recovery

Once a deadlock is detected, the OS breaks it. Two approaches:

A. Process Termination

  • Kill ALL deadlocked processes at once: Simple and immediate, but all their work is lost.
  • Kill one at a time: Kill the cheapest process to terminate, re-check for deadlock, repeat until resolved. Victim chosen by: lowest priority, shortest job, fewest resources held, or fewest steps completed.

B. Resource Preemption

  • Select a victim: Choose which process to take resources from (minimize cost/work lost).
  • Rollback: Return that process to a safe checkpoint and re-run from there (requires the system to have checkpointed progress).
  • Starvation prevention: Don't always pick the same victim — count rollbacks per process and factor that into the cost, so no process is perpetually the scapegoat.

Comparison Summary

StrategyWhen UsedOverheadConcurrencyUsed in
PreventionDesign timeLow (runtime)LowEmbedded OS
AvoidancePer requestMediumMediumReal-time OS
DetectionPeriodicallyMediumHighGeneral OS
RecoveryAfter detectionHighHighDBMSs, Linux
What real OS actually do (Linux, Windows): Most general-purpose OS simply ignore deadlocks (called the Ostrich Algorithm — bury head in sand). They rely on users to kill frozen processes or reboot. Database systems (Oracle, MySQL) actively use detection + rollback since losing a transaction is acceptable.
7 Marks Explain in detail about Deadlock System Model and Deadlock Characterization.

Deadlock System Model

A system consists of finite resources distributed among competing processes. Resources include:

  • Physical: CPU, memory, I/O devices (printers, tape drives, disks)
  • Logical: Semaphores, mutex locks, files, database records

Resource Life Cycle

  1. Request: Process requests a resource via system call (request(), semaphore-wait()). If not available, process waits.
  2. Use: Process operates on the resource (prints, reads, writes).
  3. Release: Process releases resource via system call (release(), semaphore-signal()). Another waiting process may now use it.

Deadlock Characterization

A deadlock occurs if and only if ALL four Coffman conditions hold simultaneously:

#ConditionFormal DescriptionExample
1Mutual ExclusionAt least one resource is held in non-sharable mode; only one process can use it at a timePrinter: only one job prints at a time
2Hold and WaitA process holding ≥1 resource is waiting to acquire additional resources currently held by other processesP1 holds Printer, waits for Scanner
3No PreemptionResources cannot be preempted; released only voluntarily by the holding process after completionA file lock cannot be forcibly removed
4Circular WaitExists a circular chain {P0,P1,...,Pn}: P0 waits for P1, P1 waits for P2, ..., Pn waits for P0P1→P2→P3→P1

RAG — Formal Representation

  • Vertices V = P ∪ R where P = set of processes, R = set of resource types
  • Edges E: Request edges Pi → Rj; Assignment edges Rj → Pi
  • If RAG has no cycle → no deadlock
  • If RAG has a cycle AND each resource has one instance → deadlock
  • If RAG has a cycle but resources have multiple instances → possibly deadlock (need further analysis)

Methods to Handle Deadlocks

  • Ensure system never enters deadlock: Prevention or Avoidance
  • Allow deadlock, then detect and recover: Detection + Recovery
  • Ignore deadlock: Used by most OS (Ostrich Algorithm) — reboot if needed
AKTU Key Point: For a deadlock to occur, ALL four conditions must be true simultaneously. Breaking even ONE condition prevents deadlock entirely. The Circular Wait condition is the most commonly targeted because it can be prevented through resource ordering (assign numbers to resources; always request in increasing order).
🧠 Memory Trick — Deadlock Prevention:
Break Mutual Exclusion → make resources sharable (not always possible).
Break Hold & Wait → request all resources at once before starting.
Break No Preemption → allow OS to forcibly take resources.
Break Circular Wait → number all resources; always request in increasing order. ← Most practical!
