What is an Intrusion Detection System (IDS)? Discuss its types, strengths, approaches and difficulties in anomaly detection.
7 Marks ▼
Introduction

An Intrusion Detection System (IDS) is a security tool that monitors network traffic or system activities and raises alerts when suspicious or malicious behavior is detected. It acts like a security alarm for a computer network.

Concept Booster
IDS does NOT block attacks — it only detects and alerts. The system that blocks is called IPS (Intrusion Prevention System).
Types of IDS
TypeWhere it MonitorsExample
NIDS (Network-based)Network traffic between devicesSnort, Suricata
HIDS (Host-based)Individual computer/serverOSSEC, Tripwire
Hybrid IDSBoth network + hostPrelude
Detection Approaches
ApproachHow it worksProCon
Signature-basedMatches known attack patterns (signatures)Low false positivesCan't detect new attacks
Anomaly-basedLearns normal behavior; flags deviationsDetects new/unknown attacksHigh false positives
Stateful ProtocolTracks protocol state machinesDetects protocol violationsComplex to implement
Strengths of IDS
  • Detects internal & external threats
  • Provides audit trail and logs for forensics
  • Can monitor multiple systems simultaneously
  • Complements firewalls and antivirus
  • Identifies policy violations (insider threats)
Difficulties in Anomaly Detection
  • Defining "Normal": Normal behavior changes over time (e.g., end-of-year high traffic). What's baseline?
  • High False Positive Rate: Legitimate users flagged as attackers → alert fatigue.
  • High False Negative Rate: Slow/stealthy attacks may look "normal".
  • Mimicry Attacks: Attacker crafts traffic that looks normal to IDS.
  • Encrypted Traffic: IDS cannot inspect encrypted packets easily.
  • Training Data Poisoning: If attacker poisons training data, IDS baseline is corrupted.
  • Resource Intensive: Machine learning-based anomaly detection is computationally expensive.

Important Exam Points
⚠ Common Trap: Students often confuse IDS with IPS. IDS = detect only; IPS = detect + block.
✅ NIDS vs HIDS distinction is frequently asked.
✅ Always mention "false positive" and "false negative" in anomaly detection difficulties.
Quick Revision
IDS = Detect Only NIDS = Network HIDS = Host Signature = Known attacks Anomaly = Unknown attacks Mimicry = IDS weakness
Mnemonic for IDS types: "Never Hug Hyenas" → Network, Host, Hybrid

Why is Security Hard?
7 Marks ▼
Introduction

Security is fundamentally hard because defenders must protect everything; attackers only need to find one weakness. It is an asymmetric battle.

Why Security is Hard — Key Reasons
Attacker Advantage (Asymmetry): Attacker needs ONE vulnerability. Defender must protect EVERYTHING. Cost is asymmetric.
Complexity of Systems: Modern software has millions of lines of code. Every line is a potential vulnerability. More features = more attack surface.
Human Factor: Users choose weak passwords, click phishing links, share credentials. Humans are the weakest link.
Unknown Unknowns (Zero-Days): Vulnerabilities exist that nobody knows about yet. You can't defend against what you don't know.
Evolving Threat Landscape: Attackers constantly develop new techniques. Yesterday's defense may be today's vulnerability.
Security vs Usability Trade-off: Making a system very secure often makes it hard to use. Organizations choose usability, reducing security.
Interconnected Systems: A secure system may connect to an insecure one (supply chain attacks). Security is only as strong as the weakest link.
Economic Incentives: Companies prioritize speed-to-market over security. Security costs money upfront; breaches cost money later.
Insider Threats: Trusted employees can abuse their access. Authentication doesn't stop authorized but malicious users.
Legacy Systems: Old systems with known vulnerabilities are hard to update or replace in critical infrastructure.
The CIA Triad Challenge
GoalChallenge
ConfidentialityEncryption can be broken; keys can be stolen
IntegrityData can be tampered in transit or at rest
AvailabilityDDoS can bring down any system
Important Exam Points
✅ Write at least 6–7 reasons with brief explanation for full 7 marks.
✅ Use the phrase "Attackers need to find ONE hole; defenders must plug ALL holes" — examiners love it.
✅ Mention CIA triad and its challenges.
Quick Revision
AsymmetryComplexityHuman Factor Zero-DaysEvolving ThreatsUsability Trade-off Insider ThreatsLegacy Systems

Explain Access Control List (ACL), Identity-based Access Control and Role-based Access Control along with their properties, technologies and uses.
7 Marks ▼
Introduction

Access control determines who can access what resources and what operations they can perform. It is the cornerstone of information security.

1. Access Control List (ACL)

An ACL is a table attached to each resource (file, directory, network interface) listing which users/processes have which permissions.

Structure: Resource → [User1: Read/Write, User2: Read-Only, User3: No Access]
  • Properties: Per-object permission list; supports fine-grained control; easy to revoke access
  • Technologies: Linux file ACLs (getfacl/setfacl), Windows NTFS ACLs, Cisco Router ACLs, AWS S3 bucket policies
  • Uses: File system security, network router packet filtering, cloud resource protection
  • Limitation: Hard to manage when users = thousands (doesn't scale well)
2. Identity-Based Access Control (IBAC)

Access is granted based on the identity (username/ID) of the requester. Each user has a unique identity and permissions assigned directly to it.

  • Properties: User-centric; permissions follow the individual; simple concept
  • Technologies: LDAP, Active Directory (without groups), Unix UID-based permissions
  • Uses: Small organizations, personal computers, simple systems
  • Limitation: When a user leaves, you must update permissions everywhere manually. Doesn't scale.
3. Role-Based Access Control (RBAC)

Access is granted based on the role of a user (e.g., Admin, Manager, Employee) rather than individual identity. Users are assigned roles; roles have permissions.

Flow: User → assigned Role → Role has Permissions → User gets Permissions
PropertyDescription
Least PrivilegeUsers get only permissions needed for their role
Separation of DutiesConflicting permissions can't be in one role
Role HierarchySenior roles inherit permissions of junior roles
ScalabilityAdding/removing users doesn't change permissions
  • Technologies: Active Directory Groups, AWS IAM Roles, Oracle DB Roles, Spring Security
  • Uses: Hospitals (doctor/nurse/admin roles), banks (teller/manager roles), enterprises
Comparison Table
FeatureACLIBACRBAC
BasisResource listIdentityRole
ScalabilityMediumLowHigh
ManagementPer resourcePer userPer role
Best forFiles/networksSmall systemsEnterprises
Important Exam Points
⚠ RBAC is the most asked topic. Always mention "Separation of Duties" and "Least Privilege" as RBAC properties.
✅ ACL = attached to resource; IBAC = attached to user; RBAC = attached to role.
Quick Revision
Think of a hospital: Doctors have roles (doctor-role → can view prescriptions). ACL is like a lock with a list of who has keys. IBAC = key per person. RBAC = key per job title.

Compare Access Control in Windows and UNIX.
7 Marks ▼
UNIX Access Control

UNIX uses a simple DAC (Discretionary Access Control) model with three permission sets per file:

Permission Format: [type][Owner][Group][Others]
Example: -rwxr-x---
r = read (4), w = write (2), x = execute (1)
Owner: rwx=7, Group: r-x=5, Others: ---=0 → chmod 750
  • Subjects: Users (UID) and Groups (GID)
  • Objects: Files and directories (everything is a file in UNIX)
  • Special bits: SUID (run as owner), SGID (run as group), Sticky bit (only owner can delete)
  • Root (UID=0): Superuser with unrestricted access to everything
  • ACL Extension: Extended ACLs via setfacl / getfacl
Windows Access Control

Windows uses a more complex NTFS-based ACL system with rich granularity:

  • SID (Security Identifier): Unique ID for each user/group (like UID but longer)
  • DACL (Discretionary ACL): List of ACEs (Access Control Entries) — who gets what permission
  • SACL (System ACL): For auditing — logs who accessed what
  • ACE Types: Allow or Deny specific permissions
  • Permissions: Very granular — Read, Write, Execute, Modify, Full Control, List Folder, etc.
  • Inheritance: Child objects automatically inherit parent permissions
  • Tokens: Access tokens carry user's SID + group memberships + privileges
Side-by-Side Comparison
FeatureUNIXWindows
ModelSimple DAC (9-bit)Rich ACL (DACL/SACL)
User IDUID (integer)SID (long string)
Permission SetsOwner, Group, OthersIndividual ACEs per user/group
GranularityLow (r/w/x)High (15+ permission types)
Superuserroot (UID=0)Administrator account
AuditingLimitedSACL provides audit trails
InheritanceManualAutomatic inheritance
ComplexitySimple, elegantComplex but powerful
Special BitsSUID, SGID, StickyNo direct equivalent
Extended ACLsetfacl/getfaclBuilt-in NTFS ACL
Important Exam Points
✅ UNIX: 9-bit permission model is simple but limited.
✅ Windows: DACL (who can access) + SACL (who is audited) — this distinction is important.
✅ Both use Discretionary Access Control (owner decides permissions).
Quick Revision
UNIX = rwx bitsWindows = DACL+SACLSUID = run as owner SID = Windows user IDACE = individual permission entry

What is Control Hijacking? Explain buffer overflow and various types of hijacking attacks with examples.
7 Marks ▼
Introduction

Control Hijacking is an attack where an attacker takes control of a program's execution flow by overwriting critical control data (like return addresses or function pointers) to run their own malicious code (shellcode).

Concept Booster
Stack Layout (low → high address):
[Local Variables] [Saved Frame Pointer] [Return Address] [Function Arguments]

If we overflow local variables, we can overwrite the Return Address to redirect execution.
Buffer Overflow

A buffer overflow occurs when a program writes more data into a buffer than it can hold, overwriting adjacent memory.

Program allocates a buffer of size 10 bytes on stack.
User inputs 50 bytes (e.g., using gets() or strcpy() — unsafe functions).
Extra bytes overflow into return address.
Attacker crafts input to overwrite return address with address of shellcode.
When function returns, CPU jumps to shellcode → attacker wins!
// Vulnerable code:
void foo(char *input) {
  char buf[10];
  strcpy(buf, input); // No bounds check!
}
// Input: "AAAAAAAAAA\xde\xad\xbe\xef" → overwrites return address
Types of Hijacking Attacks
Attack TypeWhat is OverwrittenExample/Detail
Stack SmashingReturn address on stackClassic buffer overflow; attacker redirects return to shellcode
Heap OverflowHeap memory objects/function pointersOverflow heap buffer to corrupt adjacent object's vtable pointer
Integer OverflowSize calculationsint size = user_input; malloc(size*4) — if size overflows, tiny buffer allocated, then overflow
Format String AttackMemory via printfprintf(user_input) — attacker uses %n to write arbitrary values to memory
Use-After-FreeFreed heap memoryAttacker allocates new object in freed memory, gains control via old pointer
Return-to-libcReturn addressInstead of shellcode, return to system() function in libc to execute /bin/sh
ROP (Return-Oriented Programming)Return address chainChain small code snippets ("gadgets") ending in RET to execute arbitrary code without injecting shellcode

Important Exam Points
⚠ Unsafe functions in C: gets(), strcpy(), sprintf(), scanf() — always mention these as causes.
✅ ROP and Return-to-libc are modern attacks when stack is non-executable (NX bit set).
✅ Draw the stack diagram — examiners give extra marks for diagrams!
Quick Revision
Buffer Overflow → overwrite return addrHeap Overflow → vtable Format String → %nROP → chain gadgetsUAF → freed memory

Explain System Call Interposition. Discuss ptrace and systrace in detail.
7 Marks ▼
Introduction

System Call Interposition is a security mechanism where a monitor intercepts system calls made by a process and decides whether to allow, deny, or modify them before they reach the OS kernel. It's like a firewall for system calls.

System Call Interposition — How It Works
ptrace

ptrace is a Linux system call that allows one process (tracer/monitor) to observe and control execution of another process (tracee). Used by debuggers like GDB.

  • How: Monitor calls ptrace(PTRACE_ATTACH, pid) to attach to a process
  • Every time tracee makes a syscall, it stops → monitor examines and decides
  • Monitor can read/write tracee's memory and registers
  • Uses: Sandboxing, debugging (GDB), strace (trace system calls), security monitoring
  • Limitations:
    • Race condition (TOCTOU): Between monitor checking and kernel executing, arguments can change in memory (in a multi-threaded process)
    • Performance overhead: Context switch for every system call
    • One-to-one: Only one tracer per process
systrace

systrace is a more advanced system call interposition tool (originally for BSD/macOS) that works at the kernel level and provides a policy-based approach.

  • Kernel-based: More efficient than ptrace (no context switch per syscall)
  • Uses policy files to define allowed/denied syscalls per application
  • Can enforce per-argument policies (e.g., allow open() only for specific directories)
  • Interactive mode: asks user on first encounter; learns policy
  • Advantages over ptrace: No TOCTOU race, kernel-level efficiency, policy-based
  • Limitation: Platform-specific; Linux moved toward seccomp for similar functionality
ptrace vs systrace
Featureptracesystrace
LevelUser-spaceKernel-space
MechanismAttach to processKernel hook
PerformanceSlow (context switch)Fast
TOCTOUVulnerableNot vulnerable
PolicyProgrammaticPolicy files
PlatformLinux/UnixBSD/macOS
Important Exam Points
⚠ TOCTOU (Time-of-Check to Time-of-Use) race condition is the KEY weakness of ptrace — must mention this.
✅ seccomp is the modern Linux equivalent of systrace — good extra point.
✅ strace uses ptrace internally — good example to cite.

Discuss Software Fault Isolation (SFI), its need, goal, solution and approach.
7 Marks ▼
Introduction

Software Fault Isolation (SFI) is a technique to confine untrusted code within a defined region of a process's address space, preventing it from corrupting or accessing memory outside its sandbox — all using software checks, not hardware.

Need for SFI
  • Running untrusted code (plugins, extensions, third-party libraries) in the same process is dangerous
  • Hardware isolation (separate processes) is too slow for frequent interactions (e.g., browser plugins)
  • We need isolation with low performance overhead
  • SFI solves this: untrusted module runs in same process but can't escape its "sandbox zone"
Goal of SFI
Guarantee that untrusted code can only read/write its designated memory region and can only call trusted code through safe, controlled interfaces.
SFI Solution & Approach

SFI assigns untrusted modules to a "fault domain" — a specific memory segment. Rules:

Segmentation: Divide address space into fixed segments. Untrusted code lives in segment N.
Instruction Rewriting: Before every store/jump in untrusted code, insert a MASK instruction that forces the target address into the safe zone.
Safe Stores: store Rd, addr becomes AND Rd, Rd, mask; store Rd, addr — addr is always in safe segment.
Safe Jumps: Indirect jumps are masked to prevent jumping to arbitrary code.
Trusted Call Stubs: Untrusted code can call trusted code only via predefined stubs (trampolines).
Verification: Before loading untrusted code, a verifier checks all instructions are properly sandboxed.
// Example: SFI-rewritten store instruction
Original: store [Reg], value
SFI: AND Reg, Reg, 0xFFFF0000 ; mask top bits to force into sandbox segment
store [Reg], value ; now guaranteed safe
Advantages & Disadvantages
AdvantagesDisadvantages
No hardware support needed~5% performance overhead (instruction insertion)
Fine-grained isolation within processVerifier must be trusted and correct
Fast communication between modulesHarder to implement on CISC architectures
Used in real systems (Native Client, WebAssembly)Code must be recompiled
Important Exam Points
✅ Real-world example: Google's Native Client (NaCl) uses SFI to run native code in browsers safely.
✅ WebAssembly is a modern descendant of SFI principles.
✅ Key insight: SFI = software-enforced isolation = mask every dangerous instruction.
Quick Revision
SFI = sandbox in-processMask instructionsFault domain No hardware neededNaCl / WebAssembly

Discuss browser isolation and remote browser isolation in detail.
7 Marks ▼
Introduction

Web browsers are major attack surfaces — malicious web content can execute code on a user's machine. Browser Isolation contains web content so even if it's malicious, it cannot harm the host system.

Browser Isolation

The principle: run web content in an isolated environment, separate from the OS and user data.

  • Process Isolation: Each browser tab runs in its own process (Chrome's sandbox model). If one tab is compromised, it can't access others or the OS.
  • Sandbox: Browser renderer process is sandboxed using OS mechanisms (seccomp, AppArmor, Windows job objects). Renderer can't make arbitrary system calls.
  • Site Isolation: Different origins run in different processes. Cross-site data theft (Spectre) mitigated.
  • Plugin Isolation: Flash/plugins run in separate processes (NPAPI deprecated for this reason).
Remote Browser Isolation (RBI)

RBI takes isolation further: the browser runs entirely on a remote server. Only a visual stream (pixels) is sent to the user's device. The user interacts via input events.

User requests a web page from their endpoint device.
Request goes to remote isolation server (cloud or on-premises).
Browser runs on isolation server, fetches and renders the page.
Only a pixel stream / DOM mirror is sent to user's device — no actual web content reaches endpoint.
Even if page has malware, it executes on the isolation server (which is disposable/containerized), not the user's PC.
FeatureLocal IsolationRemote Browser Isolation
Browser LocationUser's machineRemote server
Malware ExecutionOn user's machine (sandboxed)On remote server (never reaches user)
Zero-Day ProtectionPartialComplete (endpoint untouched)
PerformanceGoodSlight latency (pixel stream)
CostLowHigher (cloud infrastructure)
ExamplesChrome sandboxMenlo Security, Zscaler
Important Exam Points
✅ RBI is the strongest form of browser isolation — malware never reaches endpoint.
✅ Mention "pixel stream" / "DOM mirroring" as the rendering technique in RBI.
✅ Chrome uses multi-process architecture — good real-world example for local isolation.

What is Cross Site Request Forgery (CSRF)? Explain its working, examples and defenses.
7 Marks ▼
Introduction

CSRF (Cross-Site Request Forgery) is an attack that tricks an authenticated user into unknowingly submitting a malicious request. The attacker exploits the browser's behavior of automatically including cookies with requests.

Also called: Sea-Surf, XSRF, One-Click Attack, Session Riding
How CSRF Works
Victim logs into bank.com → browser stores session cookie.
Without logging out, victim visits evil.com (attacker's site).
evil.com has hidden malicious form/image/script that sends a request to bank.com (e.g., transfer money).
Browser automatically includes bank.com cookie with the request (same-origin cookie policy).
bank.com sees a valid authenticated request → executes the transfer!
<!-- Malicious HTML on evil.com -->
<img src="https://bank.com/transfer?to=attacker&amount=10000" />
<!-- Browser auto-sends bank.com cookie with this request -->
Real-World Example
  • Online banking transfer initiated without user's knowledge
  • Changing email/password of an account
  • Posting on social media as the victim
  • Buying products using victim's stored payment method
Defenses Against CSRF
DefenseHow It Works
CSRF Token (Synchronizer Token)Server generates a unique random token for each session/form. Request must include token. Attacker can't know this token (cross-origin can't read it).
SameSite Cookie AttributeSet-Cookie: session=xyz; SameSite=Strict — browser won't send cookie on cross-site requests.
Double Submit CookieCSRF token stored in both cookie and form field. Server verifies they match.
Custom Request HeadersAJAX requests with custom headers (e.g., X-Requested-With) — cross-origin can't set custom headers.
Referer/Origin Header CheckServer checks that request Origin matches server domain.
Re-authenticationFor sensitive actions (transfer, delete), require password again.
CAPTCHAProves human intent — bots/scripts can't solve it.
Important Exam Points
⚠ CSRF exploits trust in the user's browser; XSS exploits trust in the server — know the difference!
✅ CSRF token is the PRIMARY defense — always mention it first.
✅ SameSite=Strict is the modern, recommended defense.
Quick Revision
CSRF = Cookie Sent Regardless of Fraud. The cookie goes automatically — that's the bug!

Discuss SQL Injection, CSRF, XSS, Sessions and HTTP Authentication Problems.
7 Marks ▼
1. SQL Injection

SQL Injection occurs when user input is directly embedded in SQL queries without sanitization.

// Vulnerable code:
query = "SELECT * FROM users WHERE name='" + user_input + "'"
// Input: ' OR '1'='1
// Resulting query: SELECT * FROM users WHERE name='' OR '1'='1'
// Returns ALL users → authentication bypass!

Defenses: Use Prepared Statements / Parameterized Queries, input validation, ORM frameworks, WAF.

2. CSRF (Brief Recap)

Attacker tricks authenticated user's browser to send unauthorized requests. Defense: CSRF tokens, SameSite cookies.

3. XSS (Brief Recap)

Malicious JavaScript injected into web pages. Defense: Output encoding, CSP, HttpOnly cookies.

4. Session Problems
  • Session Prediction: Sequential/guessable session IDs → attacker guesses valid session. Fix: Use cryptographically random session IDs.
  • Session Fixation: Attacker sets victim's session ID before login. Fix: Regenerate session ID after login.
  • Session Hijacking: Steal session token via XSS, network sniffing. Fix: HTTPS, HttpOnly, short session expiry.
  • Session Expiry: Sessions not expired → old sessions reused. Fix: Idle timeout, absolute expiry.
5. HTTP Authentication Problems
  • Basic Auth: Credentials sent as Base64 (NOT encrypted) — easily decoded. Must use HTTPS.
  • Digest Auth: Uses MD5 hash — better than basic but MD5 is weak.
  • No Built-in Logout: HTTP is stateless — no native logout mechanism. Requires server-side session invalidation.
  • Credential Exposure: HTTP sends credentials in plaintext — need HTTPS.
  • Brute Force: No lockout in basic HTTP auth. Fix: Rate limiting, account lockout.
  • Replay Attacks: Captured credentials can be replayed. Fix: Nonces (in Digest Auth), HTTPS.
Important Exam Points
✅ For SQL Injection: always say "Prepared Statements" as the primary fix.
✅ Base64 ≠ Encryption — a common misconception about Basic Auth.
✅ Session regeneration after login is the fix for Session Fixation.

Explain SSL Encryption and the steps involved in SSL server authentication.
7 Marks ▼
Introduction

SSL (Secure Socket Layer), now succeeded by TLS (Transport Layer Security), is a cryptographic protocol that provides confidentiality, integrity, and authentication for data transmitted over a network (typically HTTPS = HTTP + TLS).

SSL/TLS Services
  • Confidentiality: Symmetric encryption (AES) after handshake
  • Integrity: MAC (Message Authentication Code) — detects tampering
  • Authentication: X.509 certificates verify server identity
SSL Server Authentication — Step by Step
Client Hello: Client sends supported TLS version, cipher suites, and a random nonce (ClientRandom) to server.
Server Hello: Server selects cipher suite, sends its own random nonce (ServerRandom), and a digital certificate (X.509) containing its public key.
Certificate Verification: Client checks:
• Certificate signed by trusted CA (Certificate Authority)
• Certificate not expired
• Domain name matches (CN/SAN)
• Certificate not revoked (CRL/OCSP)
Key Exchange: Client generates a Pre-Master Secret, encrypts it with server's public key, sends to server. (Or uses Diffie-Hellman for perfect forward secrecy.)
Session Key Generation: Both sides compute Master Secret using Pre-Master Secret + both randoms → derive symmetric session keys.
Finished Messages: Both send encrypted "Finished" message to verify handshake was not tampered with.
Secure Communication: All subsequent data encrypted with symmetric session key (e.g., AES-256).
SSL Handshake Diagram
Important Exam Points
⚠ SSL is deprecated; TLS 1.2/1.3 is current. But AKTU still calls it SSL — use both terms.
✅ Certificate verification step is key — mention CA, expiry, domain match, revocation.
✅ Symmetric key for bulk data, asymmetric key only for handshake — efficiency!

Session Hijacking

Session Hijacking = stealing a valid session token and impersonating a logged-in user.

MethodHow Token is Stolen
XSSInject script to read document.cookie and send to attacker
Network SniffingOn HTTP (no encryption), token visible in packets
Man-in-the-MiddleIntercept SSL (via evil proxy/bad cert)

Session Fixation Attack

In session fixation, the attacker sets the victim's session ID before login, then waits for the victim to authenticate.

Attacker gets a valid session ID from the server (by visiting the site).
Attacker tricks victim to use this specific session ID (via crafted link: login.php?sessionid=ATTACKER_ID).
Victim logs in — server associates attacker's session ID with victim's account.
Attacker now uses that same session ID → fully authenticated as victim!
⚠ Key difference: Hijacking = steal AFTER login. Fixation = plant BEFORE login.

What are Asymmetric Algorithms / Public Key Cryptography? Explain advantages, disadvantages and RSA algorithm with suitable examples.
7 Marks ▼
Introduction

Public Key Cryptography (Asymmetric Cryptography) uses a pair of mathematically related keys — a Public Key (shared openly) and a Private Key (kept secret). Data encrypted with one key can only be decrypted with the other.

Key Principles
  • Encrypt with Public Key → Decrypt with Private Key (Confidentiality)
  • Sign with Private Key → Verify with Public Key (Authentication / Digital Signature)
  • Based on mathematical "trapdoor" functions that are easy one way, hard to reverse
Advantages & Disadvantages
AdvantagesDisadvantages
No need to share secret key over networkMuch slower than symmetric encryption
Solves key distribution problemLarge key sizes (2048-bit RSA vs 128-bit AES)
Enables Digital SignaturesComputationally expensive
Enables Non-repudiationNot suitable for bulk data encryption
N users need only 2N keys (vs N² in symmetric)Vulnerable to quantum computing (future threat)
RSA Algorithm

RSA (Rivest-Shamir-Adleman, 1977) is based on the difficulty of factoring large numbers.

RSA Key Generation Steps
Choose two large primes p and q
Compute n = p × q (modulus)
Compute φ(n) = (p-1)(q-1) (Euler's totient)
Choose e such that 1 < e < φ(n) and gcd(e, φ(n)) = 1 (public exponent)
Compute d such that d × e ≡ 1 (mod φ(n)) (private exponent)
Public Key = (e, n); Private Key = (d, n)
Encryption: C = M^e mod n
Decryption: M = C^d mod n
Important Exam Points
✅ RSA security = hard to factor n into p and q.
✅ In practice, RSA is used only to exchange symmetric keys (hybrid encryption).
✅ Other asymmetric algorithms: ECC (Elliptic Curve), DSA, ElGamal.

Single-Key (Secret Key / Symmetric) Cryptography

Both sender and receiver use the same single secret key for both encryption and decryption.

Encryption: C = E(K, M) [C=Ciphertext, K=Key, M=Message]
Decryption: M = D(K, C) [Same key K used]
  • Types:
    • Stream Ciphers: Encrypt bit by bit (RC4, A5/1) — fast, used in mobile
    • Block Ciphers: Encrypt fixed-size blocks (AES=128-bit, DES=64-bit) — more common
  • Algorithms: DES, 3DES, AES, Blowfish, RC4, ChaCha20
  • Key Distribution Problem: Both parties must agree on the key securely — this is the fundamental weakness
  • Block Cipher Modes: ECB, CBC, CTR, GCM — how blocks are chained together

Public-Key (Asymmetric) Cryptography

Uses mathematically linked key pair: Public Key (encrypt/verify) and Private Key (decrypt/sign).

  • Applications: SSL/TLS, PGP email, SSH, code signing, digital certificates

What is Digital Signature? Explain its working, creation steps and real-world usage.
7 Marks ▼
Introduction

A Digital Signature is the electronic equivalent of a handwritten signature. It provides authentication, integrity, and non-repudiation for digital messages and documents.

Digital Signature = Hash of Message, encrypted with Sender's Private Key
Properties Provided
  • Authentication: Proves who signed (only private key holder could create the signature)
  • Integrity: Any change to message invalidates signature
  • Non-repudiation: Signer cannot deny signing (they have the only private key)
How Digital Signatures Work
SIGNING (Sender Side):
Sender hashes the message: H = Hash(M) using SHA-256
Encrypt hash with sender's private key: S = RSA_decrypt(Kpriv, H)
Send Message + Signature (S) to receiver
VERIFICATION (Receiver Side):
Decrypt signature with sender's public key: H' = RSA_encrypt(Kpub, S)
Hash the received message: H'' = Hash(M)
Compare H' and H'': if equal → signature valid; message untampered!
Digital Signature Flow
Real-World Uses
  • Email signing: S/MIME, PGP — prove email origin
  • Code signing: Software updates signed by developer — verify authenticity
  • SSL/TLS certificates: CA signs server certificate
  • Legal documents: e-Signature on contracts
  • Blockchain: Bitcoin transactions signed with private key
  • Government: Aadhaar e-Sign, digital government documents (India)
Important Exam Points
⚠ Sign with PRIVATE key, verify with PUBLIC key — opposite of encryption! Common mistake.
✅ Hashing is done BEFORE signing (efficiency — sign the hash, not the whole document).
✅ Algorithms: RSA-SHA256, DSA, ECDSA.

What is DES? Why were Double DES and Triple DES created?
7 Marks ▼
Introduction

DES (Data Encryption Standard) is a symmetric block cipher standardized by NIST in 1977. It was the dominant encryption standard for two decades before being broken.

DES — Technical Details
  • Key Size: 56 bits (64-bit key with 8 parity bits → effective 56 bits)
  • Block Size: 64 bits
  • Structure: 16 rounds of Feistel network
  • Operations: Initial Permutation → 16 Feistel rounds → Final Permutation
  • Problem: 56-bit key is too short! In 1998, EFF cracked DES in 22 hours using specialized hardware (Deep Crack). 2^56 = 72 quadrillion possibilities — brute force feasible.
Double DES — Why Created & Why it Failed

To increase security, DES was applied twice with two different keys.

Encryption: C = DES_K2(DES_K1(M)) [Effective key = 112 bits?]
Decryption: M = DES_K1⁻¹(DES_K2⁻¹(C))

Problem — Meet-in-the-Middle Attack:

  • Attacker encrypts plaintext with all 2^56 possible K1 values → stores results
  • Decrypts ciphertext with all 2^56 possible K2 values → finds match in table
  • Effective security = 2^57 (NOT 2^112 as hoped) — barely better than single DES!
  • Double DES was abandoned.
Triple DES (3DES) — Created as Fix

3DES applies DES three times to overcome the meet-in-the-middle attack.

EDE Mode: C = DES_K3(DES_K2⁻¹(DES_K1(M)))
[Encrypt with K1, Decrypt with K2, Encrypt with K3]

3-Key 3DES: K1 ≠ K2 ≠ K3 → Effective key = 168 bits (but ~112 bit security)
2-Key 3DES: K1 = K3 ≠ K2 → Effective key = 112 bits
AlgorithmKey BitsSecurity LevelStatus

Why EDE? Encrypt-Decrypt-Encrypt pattern means when K1=K2=K3, 3DES is equivalent to single DES. This ensures backward compatibility with DES systems!
Important Exam Points
⚠ Double DES is NOT secure — Meet-in-the-Middle attack reduces security to 2^57. This is the most asked exam trap.
✅ 3DES uses EDE (Encrypt-Decrypt-Encrypt) — this is a commonly asked detail.
✅ AES replaced 3DES in 2001 as the standard. NIST deprecated 3DES in 2017.

Give a short summary of IP Protocol functions.
7 Marks ▼
Introduction

The Internet Protocol (IP) is the fundamental network layer (Layer 3) protocol of the Internet. It provides addressing and routing of packets from source to destination across interconnected networks.

Key Functions of IP Protocol
FunctionDescription
AddressingEach device gets a unique IP address (IPv4: 32-bit e.g., 192.168.1.1; IPv6: 128-bit). Identifies source and destination.
RoutingIP packets are routed hop-by-hop across routers from source to destination. Routers use routing tables to decide the best path.
Packet Fragmentation & ReassemblyLarge packets are fragmented to fit smaller MTU (Maximum Transmission Unit) of intermediate networks. Reassembled at destination.
Connectionless ServiceIP is connectionless — no prior connection setup. Each packet is independently routed (may take different paths).
Best-Effort DeliveryIP does NOT guarantee delivery, order, or error-free transmission. No acknowledgment. Reliability is handled by TCP (Layer 4).
TTL (Time-to-Live)Each packet has a TTL counter. Decremented by 1 at each router. When TTL=0, packet is discarded. Prevents infinite loops.
Header ChecksumVerifies integrity of IP header (not data). If checksum fails, packet is discarded.
Protocol FieldIdentifies upper-layer protocol carried (TCP=6, UDP=17, ICMP=1). IP demultiplexes packets to correct protocol.

  • IP Spoofing: Attacker forges source IP address → used in DDoS amplification attacks
