Q 01 What is Dining Philosophers problem? Discuss the solution to Dining Philosopher's problem using monitors. 7 Marks

Concept First: What is a Monitor?

Definition — Monitor

A monitor is a high-level tool that bundles shared variables and procedures together in one safe package. The key rule: only one process can be inside the monitor at a time — mutual exclusion is built in automatically. Think of it like a room with only one door; only one person can be inside at once.

  • Monitors use condition variables to make processes wait or wake up.
  • wait() — the process pauses and exits the monitor (releases the lock), waiting to be woken up.
  • signal() — wakes up ONE process that was waiting. If nobody is waiting, nothing happens.
Memory Trick

Monitor = Room with ONE key. Only one philosopher can be inside at a time. If they can't eat yet, they drop the key (wait()) and wait outside. When someone finishes eating, they hand the key to a waiting neighbor (signal()).

Dining Philosophers Problem

Definition

The Dining Philosophers Problem (proposed by Dijkstra, 1965) models N processes competing for N shared resources. Five philosophers sit at a round table. Between each two adjacent philosophers lies one chopstick (5 chopsticks total). A philosopher needs both the chopstick on their left AND right to eat. They spend their time alternating between thinking and eating.

Simple Analogy

Think of 5 people sharing 5 forks at a circular dinner table — one fork between each pair of neighbors. You need 2 forks to eat. If everyone picks up their left fork at the same time, nobody can pick up their right fork → everyone waits forever = Deadlock.

States of a Philosopher

  • THINKING — Philosopher is not eating and not wanting a chopstick.
  • HUNGRY — Philosopher wants to eat and is trying to pick up chopsticks.
  • EATING — Philosopher has both chopsticks and is eating.
Fig 1.1 — Dining Philosophers Table (5 philosophers, 5 chopsticks)

Problems Without Synchronization

  • Deadlock: All philosophers pick up left chopstick simultaneously — none can proceed.
  • Starvation: A philosopher may never get both chopsticks if neighbors keep eating.
  • Race Condition: Two philosophers grab the same chopstick concurrently.

Solution Using Monitors

We use a monitor dp with an array state[5] and condition variables self[5] for each philosopher.

monitor dp {
  // States: THINKING, HUNGRY, EATING
  enum { THINKING, HUNGRY, EATING } state[5];
  condition self[5];   // one per philosopher

  // Initialize
  void init() {
    for (i = 0; i < 5; i++)
      state[i] = THINKING;
  }

  // Called when philosopher i wants to eat
  void pickup(int i) {
    state[i] = HUNGRY;
    test(i);                  // try to acquire both forks
    if (state[i] != EATING)
      self[i].wait();          // block if can't eat
  }

  // Called when philosopher i finishes eating
  void putdown(int i) {
    state[i] = THINKING;
    // signal neighbors they may now eat
    test((i + 4) % 5);       // left neighbor
    test((i + 1) % 5);       // right neighbor
  }

  // Check if philosopher i can eat
  void test(int i) {
    if (state[(i+4)%5] != EATING  // left not eating
     && state[i] == HUNGRY
     && state[(i+1)%5] != EATING) { // right not eating
      state[i] = EATING;
      self[i].signal();         // wake philosopher i
    }
  }
}

// Philosopher i process:
do {
  think();
  dp.pickup(i);    // try to eat
  eat();
  dp.putdown(i);   // release forks
} while (true);

How it Works — Step by Step

  1. Philosopher i calls pickup(i): sets their state to HUNGRY ("I want to eat").
  2. test(i) checks: are BOTH neighbors NOT eating right now? If yes → state changes to EATING.
  3. If neighbors are eating, philosopher waits on self[i] (they leave the monitor and sleep).
  4. After eating, putdown(i) sets state back to THINKING and calls test() on both neighbors.
  5. If a neighbor was waiting and can now eat (both their neighbors are free), they get woken up (signal()).
Why No Deadlock?

In the naive chopstick solution, a philosopher can grab one chopstick and wait for the second — this is "hold and wait" which causes deadlock. The monitor solution is atomic: either you get permission to eat (both chopsticks logically granted at once) or you wait without holding anything. No hold-and-wait = No deadlock.

Why Monitor Solution is Better

PropertyMonitor Solution
Mutual ExclusionGuaranteed automatically by monitor
DeadlockAvoided — philosopher waits using wait(), not busy-waiting
StarvationMay still occur; can be solved by adding FIFO queue in condition variable
ComplexitySimple and readable compared to semaphore solution
Exam Tip

The monitor solution avoids deadlock because a philosopher either gets BOTH chopsticks (logically, at once via the test() function) or waits without holding any. This breaks the "hold and wait" condition needed for deadlock. Starvation is still theoretically possible but can be fixed by using a FIFO (first-come-first-served) queue for the condition variable.

Q 02 Discuss Mutual Exclusion implementation with test_and_set() instruction. 7 Marks

Concept First: Hardware Support for Synchronization

Software solutions like Dekker's and Peterson's algorithms work but have a big weakness: they rely on busy-waiting (wasting CPU in a loop) and can break on modern CPUs that reorder instructions. Modern CPUs provide atomic hardware instructions — operations that complete in one uninterruptible step. The most commonly asked one is test_and_set().

Memory Trick

Atomic = Cannot be interrupted in the middle. Like a light switch — it's either ON or OFF, never half-way. test_and_set() reads a lock value and sets it to true in one atomic step — no other process can sneak in between.

test_and_set() Instruction

Definition

test_and_set() is an atomic (indivisible) hardware instruction that does THREE things in one uninterruptible step: (1) reads the current value of a boolean variable, (2) sets it to true, and (3) returns the old value. No context switch can happen in between these steps.

Think of it like this

Imagine checking if a bathroom is free and locking the door — all in one instant motion. That's what test_and_set does: it simultaneously checks (test) and locks (set) the shared variable. Nobody else can check/set at the exact same moment.

// Hardware definition of test_and_set (executed atomically)
boolean test_and_set(boolean *target) {
  boolean rv = *target;   // read current value
  *target = true;          // always set to true
  return rv;               // return old value
}
// This entire function executes as ONE CPU instruction

Mutual Exclusion Using test_and_set()

A shared boolean variable lock is initialized to false. A process acquires the lock only when test_and_set() returns false.

boolean lock = false;   // shared variable, initially free

// Process Pi:
do {
  // ENTRY SECTION — busy wait until lock is free
  while (test_and_set(&lock));   // spin until false returned

  // CRITICAL SECTION
  // ... access shared resource ...

  // EXIT SECTION — release lock
  lock = false;

  // REMAINDER SECTION
} while (true);
Fig 2.1 — Flow of test_and_set() based Mutual Exclusion

Why It Ensures Mutual Exclusion

  • If lock == false (free): test_and_set() returns false AND sets it to true in one step → process enters CS. Lock is now true so others must wait.
  • If lock == true (busy): test_and_set() returns true → the while loop keeps spinning (busy waiting).
  • No two processes can both get false back simultaneously — atomicity guarantees this.
Remember: How a process enters/exits

Enter CS: test_and_set returns false → lock was free → you enter (lock is now true). Exit CS: set lock = false → you release it for the next process.

Bounded Waiting Problem

Problem with Simple test_and_set

The basic version above does NOT guarantee bounded waiting — a process might spin forever if other processes keep grabbing the lock repeatedly. To fix this, we use a waiting array: each process marks itself as waiting. When a process exits the CS, it checks the waiting array in order and directly hands the lock to the next waiting process rather than releasing it freely.

Modified Solution with Bounded Waiting

boolean waiting[n];  // waiting[i] = true if Pi is waiting
boolean lock;        // shared lock

// Entry section for process Pi:
waiting[i] = true;
key = true;
while (waiting[i] && key)
  key = test_and_set(&lock);
waiting[i] = false;

// Exit section:
j = (i + 1) % n;
while ((j != i) && !waiting[j])
  j = (j + 1) % n;
if (j == i)
  lock = false;       // no one waiting, free lock
else
  waiting[j] = false; // let next waiting process in

Advantages & Disadvantages

AspectDetails
Mutual Exclusion✓ Guaranteed by atomicity of hardware instruction
Progress✓ If CS is free, a waiting process will eventually enter
Bounded Waiting✗ Not guaranteed in basic version; ✓ with waiting array
Busy Waiting✗ Process spins in loop, wastes CPU cycles
Applicable toWorks for any number of processes (unlike software solutions)
Q 03 State the Critical Section problem. Illustrate the software-based solution to the Critical Section problem. 7 Marks

Critical Section Problem

Definition

The Critical Section (CS) Problem is a synchronization problem where n processes share data. The section of code where a process accesses/modifies shared data is its critical section. The problem is to design a protocol so that no two processes execute their CS simultaneously.

Structure of a Process

do {
  // ENTRY SECTION — request to enter CS
  // ...
    // CRITICAL SECTION
    // Access shared resources here
  // ...
  // EXIT SECTION — signal leaving CS
  // ...
  // REMAINDER SECTION — rest of code
} while (true);

Three Conditions for a Valid Solution

Required Conditions
  • Mutual Exclusion: At most ONE process may execute in its CS at any time.
  • Progress: If no process is in CS and some wish to enter, selection must happen in finite time.
  • Bounded Waiting: A process requesting entry must enter within a finite number of times others enter.

Software Solution 1: Turn Variable (Strict Alternation)

Uses a shared variable turn to alternate between P0 and P1.

int turn = 0;   // 0 = P0's turn, 1 = P1's turn

// Process P0:
do {
  while (turn != 0);   // wait for my turn
  /* CRITICAL SECTION */
  turn = 1;             // give turn to P1
  /* REMAINDER SECTION */
} while (true);

// Process P1:
do {
  while (turn != 1);   // wait for my turn
  /* CRITICAL SECTION */
  turn = 0;             // give turn to P0
  /* REMAINDER SECTION */
} while (true);
Problem

Violates Progress — if P1 doesn't want CS, P0 can never enter again (stuck waiting for turn=0 which never comes again once P1 is done).

Software Solution 2: Flag Variable

Each process uses a flag[] to indicate its intent to enter CS.

boolean flag[2] = {false, false};

// Process P0:
do {
  flag[0] = true;              // I want to enter
  while (flag[1]);             // wait if P1 wants in
  /* CRITICAL SECTION */
  flag[0] = false;
  /* REMAINDER */
} while (true);
Problem

Violates Mutual Exclusion — if both set flag to true simultaneously, both can enter CS. Also can cause deadlock.

Software Solution 3: Peterson's Algorithm ✓ (Correct)

Combines turn and flag[] for a complete correct solution for 2 processes.

int turn;
boolean flag[2] = {false, false};

// Process P0:
do {
  flag[0] = true;             // I want to enter
  turn = 1;                    // give priority to P1
  while (flag[1] && turn==1); // wait if P1 wants and it's P1's turn
  /* CRITICAL SECTION */
  flag[0] = false;            // done, release
  /* REMAINDER SECTION */
} while (true);

// Process P1:
do {
  flag[1] = true;
  turn = 0;                    // give priority to P0
  while (flag[0] && turn==0);
  /* CRITICAL SECTION */
  flag[1] = false;
  /* REMAINDER SECTION */
} while (true);
Fig 3.1 — Peterson's Algorithm: Two-process mutual exclusion

How Peterson's Algorithm Works (Plain English)

  • Each process says "I want in" (flag[i] = true) and then politely says "but you can go first" (turn = other process).
  • A process waits only if: the OTHER process wants in AND it's the other's turn.
  • If only one process wants in → it enters immediately (the other's flag is false).
  • If both want in at the same time → whichever set turn last will wait (the other goes first).

Proof that all 3 Conditions are Met

  • Mutual Exclusion ✓: P0 enters CS only when flag[1]=false (P1 doesn't want in) OR turn=0 (it's P0's turn). P1 entering requires turn=1. Both conditions can't hold at once, so they can't both be in CS.
  • Progress ✓: If P1 is not interested (flag[1]=false), P0 skips the while loop and enters immediately — no unnecessary waiting.
  • Bounded Waiting ✓: When P0 is waiting, P1 can enter CS at most once before P0 gets in (because P1 sets turn=0 on its next iteration, giving P0 priority).
Memory Trick — Peterson's in One Line

"I raise my flag 🏳️ AND give YOU the turn. I wait only if your flag is up AND it's your turn."

Q 04 What is a Critical Section problem? Give the conditions that a solution to the critical section problem must satisfy. 7 Marks

Critical Section Problem

Definition

Consider a system with n processes {P0, P1, …, Pn-1}. Each process has a segment of code called its critical section in which it may be changing shared variables, updating a table, writing a file, etc. The Critical Section Problem is to design a protocol that allows processes to cooperate without conflict when accessing shared data.

Why Is It a Problem?

  • Multiple processes run concurrently and may try to access same shared data simultaneously.
  • Without control, concurrent access can lead to race conditions — output depends on execution order.
  • Example: Two processes both increment counter → one update may be lost.
Fig 4.1 — Two processes competing for a Shared Resource via Critical Sections

Three Must-Satisfy Conditions

1. Mutual Exclusion

Condition 1

If process Pi is in its critical section, no other process can be in its critical section at the same time. Only ONE process in CS at any moment. Think: Only one person in the bathroom at a time.

2. Progress

Condition 2

If no process is currently in CS and some processes want to enter, the decision of who enters must happen in finite time — it cannot be postponed forever. Only processes that are NOT in their remainder section can participate in this decision. Think: If the bathroom is free, someone waiting must be allowed in — you can't just keep everyone waiting outside forever.

3. Bounded Waiting

Condition 3

After a process requests to enter CS, there is a limit on how many times other processes can enter before it gets its turn. This prevents a process from waiting forever (starvation). Think: At a ticket counter, there's a rule that you can't skip the same person more than N times.

Additional Assumptions

  • Each process executes at a nonzero speed (they keep running; they don't freeze).
  • No assumption is made about which process is faster than others.
  • A process may crash in the remainder section, but NOT inside the critical section.
Memory Trick — MPB

Remember the 3 conditions as MPB: Mutual Exclusion (only 1 at a time), Progress (if CS free, someone must enter), Bounded waiting (no one waits forever). A solution is only valid if ALL THREE are satisfied.

Q 05 Explain what semaphores are, their usage, implementation to avoid busy waiting, and binary semaphores. 7 Marks

What is a Semaphore?

Definition

A semaphore (proposed by Dijkstra, 1965) is a synchronization tool — simply an integer variable S. It can only be accessed using two special atomic operations: wait() (also called P or down — decrements S) and signal() (also called V or up — increments S). No process can directly change S in any other way.

Simple Analogy

Think of a semaphore as a counter for available parking spots. wait() = a car enters (count goes down). signal() = a car leaves (count goes up). If count = 0, new cars must wait outside.

Basic Operations

// wait() — also called P(), down()
void wait(int *S) {
  while (*S <= 0);   // busy wait — spin until S > 0
  (*S)--;            // decrement
}

// signal() — also called V(), up()
void signal(int *S) {
  (*S)++;            // increment (release)
}

Types of Semaphores

TypeRangeUsage
Binary Semaphore0 or 1 onlyMutual exclusion (like a mutex/lock)
Counting Semaphore0 to N (any integer)Control access to a resource with N instances

Binary Semaphore for Mutual Exclusion

Semaphore mutex = 1;   // initialized to 1

// Process Pi:
do {
  wait(mutex);         // enter CS — decrements to 0
  /* CRITICAL SECTION */
  signal(mutex);       // exit CS — increments to 1
  /* REMAINDER SECTION */
} while (true);

Counting Semaphore for Resource Management

Semaphore resource = N;   // N = number of instances

// To use a resource:
wait(resource);   // decrements count
/* use resource */
signal(resource); // increments count

Implementation Without Busy Waiting

The basic semaphore above uses busy waiting — the process keeps looping (spinning) until it can enter, wasting CPU time. A smarter approach uses a waiting queue: if a process can't proceed, the OS puts it to sleep (blocks it) and wakes it up later when the resource is free.

// Semaphore structure with queue:
typedef struct {
  int value;          // semaphore value
  struct process *list; // waiting queue
} Semaphore;

void wait(Semaphore *S) {
  S->value--;
  if (S->value < 0) {
    // add this process to S->list
    block();   // suspend process (OS removes from CPU)
  }
}

void signal(Semaphore *S) {
  S->value++;
  if (S->value <= 0) {
    // remove a process P from S->list
    wakeup(P); // resume P (OS adds to ready queue)
  }
}
Fig 5.1 — Semaphore with blocking (no busy waiting): P0 enters CS, P1 blocks; P0 wakes P1 via signal

Usage: Semaphore for Ordering (Synchronization)

Semaphore synch = 0;   // initially 0

// Ensure S2 executes AFTER S1:

// Process P1:
S1;
signal(synch);   // wake P2

// Process P2:
wait(synch);     // block until P1 signals
S2;

Advantages & Disadvantages

  • ✓ Can manage multiple resource instances — just initialize S to N (number of instances).
  • ✓ Blocking implementation eliminates busy waiting — process sleeps instead of spinning.
  • ✓ Works for any number of processes (unlike Peterson's which only works for 2).
  • ✗ Risk of deadlock if wait() and signal() are used in the wrong order.
  • ✗ Easy to misuse — no compiler enforcement; programmer must be careful.
Memory Trick — P and V

P (wait/down) = "Please wait" — decrements, may block. V (signal/up) = "You may go" — increments, may wake someone. These come from Dutch: Proberen (to test) and Verhogen (to increment), named by Dijkstra.

Q 06 What is Producer Consumer problem? How can it illustrate the classical problem of synchronization? Explain. 7 Marks

Producer-Consumer Problem

Definition

The Bounded Buffer / Producer-Consumer Problem is a classic synchronization problem. A producer process creates data items and puts them into a shared buffer. A consumer process removes and uses those items. The buffer has a fixed size N — it can't hold more than N items at once.

Real World Example

Think of a factory assembly line: workers (producers) place items on a conveyor belt (buffer of size N); packers (consumers) take items off the other end. If the belt is full, workers stop. If it's empty, packers wait.

Constraints

  • Producer must not produce if buffer is full (wait).
  • Consumer must not consume if buffer is empty (wait).
  • Producer and Consumer must not access buffer simultaneously (mutual exclusion).
Fig 6.1 — Bounded Buffer: Producer puts at 'in', Consumer takes from 'out'

How It Illustrates Classical Synchronization Problems

  • Mutual Exclusion: Buffer is a shared resource — only one process should access it at a time.
  • Synchronization: Producer must wait if buffer full; Consumer must wait if buffer empty.
  • Deadlock Risk: If both processes wait for each other indefinitely.
  • Starvation Risk: One process keeps accessing while other waits.

Solution Using Semaphores

Semaphore mutex = 1;   // mutual exclusion for buffer access
Semaphore full  = 0;   // counts full slots (items in buffer)
Semaphore empty = N;   // counts empty slots (N = buffer size)
int in = 0, out = 0;  // circular buffer pointers

// PRODUCER process:
do {
  item = produce_item();

  wait(empty);           // wait if no empty slot
  wait(mutex);           // lock buffer

  buffer[in] = item;
  in = (in + 1) % N;

  signal(mutex);         // unlock buffer
  signal(full);          // notify one more item available
} while (true);

// CONSUMER process:
do {
  wait(full);            // wait if no item available
  wait(mutex);           // lock buffer

  item = buffer[out];
  out = (out + 1) % N;

  signal(mutex);         // unlock buffer
  signal(empty);         // notify one more slot available

  consume_item(item);
} while (true);

Semaphore Roles Explained

SemaphoreInitial ValuePurpose
mutex1Binary semaphore — ensures only one process accesses buffer at a time
full0Counts number of items in buffer; consumer waits when full=0
emptyNCounts empty slots; producer waits when empty=0
Important — Order of wait()

Always call wait(full/empty) BEFORE wait(mutex). Reversing this order can cause deadlock — producer holds mutex and waits for empty, while consumer holds mutex and waits for full.

Q 07 Explain in detail about the Mutual Exclusion and Critical Section Problem. 7 Marks

Mutual Exclusion

Definition

Mutual Exclusion is a property of concurrent programming that ensures only ONE process or thread can access a shared resource or execute a critical section at any given time. It prevents race conditions and data inconsistency.

Why Mutual Exclusion is Needed

Consider two processes both executing counter++ on a shared variable:

// Both P0 and P1 execute: counter++ (counter = 5 initially)
// Machine-level execution:

// P0 reads counter → register0 = 5
// P1 reads counter → register1 = 5  [CONTEXT SWITCH!]
// P0 increments   → register0 = 6
// P0 writes back  → counter = 6
// P1 increments   → register1 = 6
// P1 writes back  → counter = 6  ← Should be 7! WRONG!

Race Condition

Definition — Race Condition

A race condition occurs when multiple processes access and manipulate shared data concurrently and the final result depends on the order of execution. The output is non-deterministic and incorrect.

Critical Section Problem — Detailed

Consider n processes {P0, P1, …, Pn-1} running concurrently. Each process structure is:

do {
  /* ━━━━━━━━━━━━━━━━━━━━━━━━━ */
  /*  Entry Section            */
  /*  Request to enter CS      */
  /* ━━━━━━━━━━━━━━━━━━━━━━━━━ */
     /* CRITICAL SECTION */
     /* Access shared data, files, devices */
  /* ━━━━━━━━━━━━━━━━━━━━━━━━━ */
  /*  Exit Section             */
  /*  Release access to CS     */
  /* ━━━━━━━━━━━━━━━━━━━━━━━━━ */
  /* Remainder Section          */
  /* Non-critical code          */
} while (true);

Approaches to Achieve Mutual Exclusion

ApproachMethodExample
Disable InterruptsPrevent context switch in CSCLI/STI on x86 (only for single-CPU)
Software SolutionsFlag & turn variablesPeterson's Algorithm, Dekker's
Hardware InstructionsAtomic instructionstest_and_set(), compare_and_swap()
SemaphoresOS-provided sync primitivemutex semaphore with wait/signal
MonitorsHigh-level language constructJava synchronized, monitor keyword

Conditions for Valid Mutual Exclusion Solution

  1. Mutual Exclusion — At most one process executes in CS at any time.
  2. Progress — If CS is free and processes want in, a decision is made in finite time.
  3. Bounded Waiting — A process requesting CS must be allowed in within finite time.
  4. No assumption on speed — Solution works regardless of relative CPU speeds.

Consequences of Poor Mutual Exclusion

  • Data Corruption: Shared variable ends up with wrong value.
  • Deadlock: Two processes each hold a resource and wait for the other.
  • Starvation: A process waits indefinitely to enter CS.
  • Livelock: Processes change states repeatedly without making progress.
Q 08 Explain in detail about the Dining Philosopher Problem. 7 Marks

Problem Statement

Definition

The Dining Philosophers Problem (Dijkstra, 1965) models resource allocation among competing processes. Five philosophers sit at a circular table. Each has a plate of spaghetti. Between adjacent philosophers are 5 chopsticks (one between each pair). A philosopher needs both left and right chopsticks to eat. They spend time either thinking or eating.

Problems That Arise

1. Deadlock

  • All 5 philosophers simultaneously pick up their left chopstick.
  • Each waits for the right chopstick which is held by the next philosopher.
  • Circular wait → deadlock — none can eat.

2. Starvation

  • Even without deadlock, a philosopher may wait indefinitely if neighbors keep eating.
  • This is starvation — a process is denied resources indefinitely.

Naive (Wrong) Solution

// Philosopher i (WRONG — causes deadlock):
do {
  think();
  pick_up(chopstick[i]);           // left chopstick
  pick_up(chopstick[(i+1)%5]);     // right chopstick
  eat();
  put_down(chopstick[i]);
  put_down(chopstick[(i+1)%5]);
} while (true);
// If all pick left simultaneously → DEADLOCK!

Correct Solutions

Solution 1: Allow at most 4 philosophers to sit at once

  • Use a counting semaphore initialized to 4.
  • At most 4 can attempt to pick up chopsticks → at least one will succeed.
  • Breaks circular wait condition of deadlock.

Solution 2: Asymmetric Solution

  • Odd-numbered philosophers pick left then right.
  • Even-numbered philosophers pick right then left.
  • Breaks circular dependency — prevents deadlock.

Solution 3: Only pick up if BOTH are available (Monitor)

// Philosopher can pick chopsticks only if BOTH are free:
void pickup(int i) {
  state[i] = HUNGRY;
  test(i);           // check both neighbors not eating
  if (state[i] != EATING)
    self[i].wait();   // wait atomically inside monitor
}

Deadlock Conditions in Dining Philosophers

Deadlock ConditionIn Dining Philosophers
Mutual ExclusionEach chopstick can be held by only one philosopher
Hold and WaitPhilosopher holds left chopstick, waits for right
No PreemptionChopsticks can't be forcibly taken away
Circular WaitP0 waits for P1, P1 for P2, ..., P4 for P0
Key Insight

The Dining Philosophers Problem shows that just ensuring mutual exclusion is NOT enough for a complete synchronization solution. We must also prevent deadlock and starvation. The Monitor-based solution (Q1) is the most elegant and correct approach.

Q 09 Explain in detail about the Inter Process Communication (IPC) Models and Schemes. 7 Marks

What is Inter-Process Communication (IPC)?

Definition

Inter-Process Communication (IPC) is a mechanism that allows processes to communicate and synchronize their actions when running concurrently. Processes are either independent (do not share data) or cooperating (share data and need communication). IPC is needed for cooperating processes.

Why IPC is Needed

  • Information Sharing: Multiple processes may need the same data (e.g., shared file).
  • Computation Speedup: Task divided among multiple processes for parallelism.
  • Modularity: System divided into separate processes/modules.
  • Convenience: User runs multiple tasks simultaneously (editor + compiler).

Two Fundamental IPC Models

Fig 9.1 — IPC Models: Shared Memory (left) vs Message Passing (right)

Model 1: Shared Memory

Cooperating processes share a region of memory. Data exchange happens by reading/writing to this shared space. OS sets up the shared region; processes then communicate directly.

  • Faster — no kernel calls per data transfer after setup.
  • Requires explicit synchronization (semaphores, mutexes) to prevent race conditions.
  • Example: POSIX shmget(), shmat(); System V shared memory.
  • Classic problem: Producer-Consumer with shared buffer.

Model 2: Message Passing

Processes communicate by sending and receiving messages through the OS kernel. No shared memory is required.

  • send(message) — send a message to another process.
  • receive(message) — receive a message from another process.
  • Safer — OS mediates all communication.
  • Useful for distributed systems and inter-machine communication.
  • Example: Pipes, message queues, sockets, signals.

Q 10 Explain producer consumer problem and its solution using semaphore. 7 Marks

Producer-Consumer Problem (Bounded Buffer)

Problem Statement

A Producer process generates data and places it in a shared buffer of size N. A Consumer process removes data from the buffer. Synchronization is needed to prevent: (1) Producer overflow when buffer full, (2) Consumer underflow when buffer empty, (3) Simultaneous access to the buffer.

Three Synchronization Requirements

  1. Buffer Full Handling: Producer blocks when buffer is full, waits until consumer removes an item.
  2. Buffer Empty Handling: Consumer blocks when buffer is empty, waits until producer adds an item.
  3. Mutual Exclusion: Only one process (producer or consumer) accesses the buffer at a time.

Semaphore Variables

VariableTypeInit ValuePurpose
mutexBinary1Mutual exclusion for buffer access
fullCounting0Number of filled slots (items produced)
emptyCountingNNumber of empty slots (space available)

Complete Semaphore Solution

// Initialization
Semaphore mutex = 1;   // binary lock
Semaphore full  = 0;   // initially 0 items
Semaphore empty = N;   // initially N empty slots
item buffer[N];
int in = 0, out = 0;

/* ─── PRODUCER ─── */
void producer() {
  item nextProduced;
  while (true) {
    nextProduced = produce_item();   // generate item

    wait(empty);    // P(empty): wait if no space
    wait(mutex);    // P(mutex): lock buffer

    buffer[in] = nextProduced;       // add to buffer
    in = (in + 1) % N;              // advance pointer

    signal(mutex);  // V(mutex): unlock buffer
    signal(full);   // V(full): notify consumer
  }
}

/* ─── CONSUMER ─── */
void consumer() {
  item nextConsumed;
  while (true) {
    wait(full);     // P(full): wait if buffer empty
    wait(mutex);    // P(mutex): lock buffer

    nextConsumed = buffer[out];      // remove from buffer
    out = (out + 1) % N;            // advance pointer

    signal(mutex);  // V(mutex): unlock buffer
    signal(empty);  // V(empty): notify producer

    consume_item(nextConsumed);     // process item
  }
}

How to read the trace

full = number of items currently in buffer. empty = number of free slots. mutex = always returns to 1 after each operation (lock released). Note that full + empty always = N (buffer size). When empty=0, producer is blocked. When full=0, consumer is blocked.

Critical Order Rule

Always perform wait(full) or wait(empty) before wait(mutex). If mutex is acquired first and then the process blocks on full/empty — the other process can never get mutex → deadlock.

Q 11 Explain dining philosopher problem and its solution using semaphore. 7 Marks

Problem Recap

Five philosophers sit around a table. Five chopsticks are placed between them (one between each adjacent pair). A philosopher needs both adjacent chopsticks to eat. They alternate between thinking and eating.

Semaphore Representation

// Each chopstick is a binary semaphore
Semaphore chopstick[5] = {1, 1, 1, 1, 1}; // all free initially

// Philosopher i (BASIC — causes deadlock):
do {
  think();
  wait(chopstick[i]);           // pick left
  wait(chopstick[(i+1) % 5]);   // pick right
  eat();
  signal(chopstick[i]);         // put left
  signal(chopstick[(i+1) % 5]); // put right
} while (true);
// PROBLEM: all pick left → circular wait → DEADLOCK

Correct Solutions Using Semaphores

Solution 1: Allow at Most 4 Philosophers (Counting Semaphore)

Semaphore chopstick[5] = {1,1,1,1,1};
Semaphore room = 4;  // at most 4 philosophers at table

// Philosopher i:
do {
  think();
  wait(room);                   // only 4 can attempt
  wait(chopstick[i]);
  wait(chopstick[(i+1)%5]);
  eat();
  signal(chopstick[i]);
  signal(chopstick[(i+1)%5]);
  signal(room);                  // done, leave table
} while (true);
// Guarantees: at least one philosopher can always eat

Solution 2: Asymmetric Assignment

// Philosopher i:
do {
  think();
  if (i % 2 == 0) {             // EVEN: left then right
    wait(chopstick[i]);
    wait(chopstick[(i+1)%5]);
  } else {                       // ODD: right then left
    wait(chopstick[(i+1)%5]);
    wait(chopstick[i]);
  }
  eat();
  signal(chopstick[i]);
  signal(chopstick[(i+1)%5]);
} while (true);
// Breaks circular wait → no deadlock

Solution 3: State-Based with Three States

int state[5] = {THINKING, ...};  // THINKING=0, HUNGRY=1, EATING=2
Semaphore mutex = 1;
Semaphore s[5] = {0,0,0,0,0};   // per-philosopher semaphores

void test(int i) {
  if (state[i] == HUNGRY
   && state[(i+4)%5] != EATING
   && state[(i+1)%5] != EATING) {
    state[i] = EATING;
    signal(s[i]);  // allow philosopher i to eat
  }
}

void pickup(int i) {
  wait(mutex);
  state[i] = HUNGRY;
  test(i);
  signal(mutex);
  wait(s[i]);    // block if couldn't eat
}

void putdown(int i) {
  wait(mutex);
  state[i] = THINKING;
  test((i+4)%5);  // check left neighbor
  test((i+1)%5);  // check right neighbor
  signal(mutex);
}

Q 12 Explain the challenges of achieving mutual exclusion in concurrent programming. 7 Marks

Introduction

Making sure only one process enters the critical section at a time sounds simple — but in practice it's tricky. A correct solution must also be fair, efficient, and free from bugs like deadlock and starvation. Here are the main challenges programmers face:

Key Challenges

1. Race Conditions

Challenge

When two processes read and modify shared data at the same time (without synchronization), the final result depends on which one ran at what exact moment — making the output unpredictable and often wrong. This is called a race condition. Think: two people editing the same Google Doc line at the same moment — one person's change gets lost.

// Race condition example:
// Both P0 and P1 execute: counter++ (shared, counter=5)
// Possible result: 6 instead of expected 7
// Because: Load-Modify-Store is NOT atomic!

2. Deadlock

Challenge

Deadlock is when two or more processes are permanently stuck — each waiting for the other to release a resource, so none can proceed. Bad mutex design can itself cause deadlock. Think: two people in a narrow hallway, each waiting for the other to step aside — neither moves.

  • P0 holds R1, waits for R2; P1 holds R2, waits for R1 → neither can proceed.
  • Solution: Impose resource ordering, use timeouts, or use lock-free algorithms.

3. Starvation (Indefinite Postponement)

  • A process keeps waiting for the critical section indefinitely because other processes keep getting priority ahead of it.
  • Even if mutual exclusion is working perfectly, unfair scheduling can cause starvation.
  • Solution: Bounded waiting must be guaranteed — use FIFO queues in semaphores so everyone gets a fair turn.

4. Busy Waiting (Spinlock Overhead)

  • Many simple solutions use busy waiting — process repeatedly checks a condition in a loop.
  • Wastes CPU cycles — processor could be doing useful work for another process.
  • Acceptable for short waits; must use block()/sleep() for longer waits.

5. Atomicity Issues

Challenge

Software solutions assume that reading AND writing a variable happen as one uninterruptible step (atomically). But on modern CPUs, instructions can be reordered or cached, breaking this assumption. Without memory barriers or atomic hardware instructions, software-only solutions like Peterson's can fail silently on modern hardware.

6. Priority Inversion

  • A low-priority process holds a lock needed by a high-priority process.
  • High-priority process must wait for low-priority → priority system violated.
  • Famous example: Mars Pathfinder mission (1997) — resets due to priority inversion.
  • Solution: Priority inheritance protocol — lock holder temporarily inherits higher priority.

7. Scalability on Multiprocessors

  • On multi-core CPUs, disabling interrupts only works on the local CPU — not other cores.
  • Cache coherence issues: different cores may have stale copies of shared variables.
  • Need memory barriers (fence instructions) and hardware-supported atomics.

8. Livelock

  • Processes are NOT blocked, but they keep changing state without ever making actual progress — like two people in a hallway who keep moving aside in the same direction to let each other pass, forever.
  • Example: Two processes both detect a conflict and both yield at the same time, forever, repeatedly.
  • Solution: Randomized backoff — each process waits a random amount of time before retrying (Ethernet CSMA/CD uses this).

Q 13 Compare and contrast Dekker's and Peterson's algorithms for mutual exclusion, considering their advantages and limitations. 7 Marks

Introduction

Both Dekker's and Peterson's algorithms are pure software solutions to the mutual exclusion (critical section) problem for exactly 2 processes. They use only shared variables — no special hardware instructions needed. Peterson's is the improved, cleaner version of Dekker's.

Dekker's Algorithm

Definition

Dekker's Algorithm (1960s) was the first ever correct software solution for mutual exclusion between two processes. It uses a flag[] array (to show intent) and a turn variable (to break ties). When both processes want in at the same time, the one whose turn it is NOT backs off temporarily.

boolean flag[2] = {false, false};
int turn = 1;

// Process P0 (Process P1 is mirror image):
do {
  flag[0] = true;             // P0 wants to enter
  while (flag[1]) {           // if P1 also wants in...
    if (turn == 1) {          // and it's P1's turn
      flag[0] = false;       // P0 backs off temporarily
      while (turn == 1);      // wait for turn to change
      flag[0] = true;        // re-assert intent
    }
  }
  /* CRITICAL SECTION */
  turn = 1;                   // give turn to P1
  flag[0] = false;           // done, clear intent
  /* REMAINDER */
} while (true);

Peterson's Algorithm

Definition

Peterson's Algorithm (G. Peterson, 1981) is a much simpler and more elegant solution. Instead of backing off like Dekker's, a process sets its flag to true AND immediately sets turn to the OTHER process — saying "I want in, but you can go first if you want." The waiting condition is just a single while loop.

boolean flag[2] = {false, false};
int turn;

// Process P0:
do {
  flag[0] = true;              // I want CS
  turn = 1;                     // but yield turn to P1
  while (flag[1] && turn==1);  // wait only if P1 wants AND it's P1's turn
  /* CRITICAL SECTION */
  flag[0] = false;
  /* REMAINDER */
} while (true);

Advantages and Limitations

Dekker's Algorithm

  • ✓ Historically significant — first correct software ME solution.
  • ✓ Uses only shared variables — no hardware support.
  • ✗ Complex and hard to understand — difficult to verify correctness.
  • ✗ Difficult to extend beyond 2 processes.
  • ✗ Busy waiting wastes CPU cycles.

Peterson's Algorithm

  • ✓ Simpler, cleaner, and more elegant.
  • ✓ Easier to understand and verify.
  • ✓ Bounded waiting — a process waits at most one turn of the other.
  • ✗ Only for 2 processes in basic form.
  • ✗ Busy waiting (spinlock) — not efficient for long waits.
  • ✗ On modern architectures, compiler/CPU reordering can violate correctness — needs volatile or memory barriers.

Common Limitation: Modern CPUs

Modern Architecture Issue

Both algorithms assume that memory writes are instantly visible to all processors. But modern CPUs have store buffers, caches, and out-of-order execution — a write by one CPU may not be seen by another CPU immediately. On modern systems, both algorithms need memory fence/barrier instructions to work correctly. This is why hardware instructions (test_and_set, compare-and-swap) or OS primitives (mutexes, semaphores) are used in practice.

One-Line Summary to Remember

Dekker = First solution, complex (backs off flag → waits for turn → reasserts flag). Peterson = Simpler, elegant (set flag + yield turn → single while loop). Both: only 2 processes, busy waiting, need memory barriers on modern CPUs.
